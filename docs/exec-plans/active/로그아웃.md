### BE 구현 현황 (직접 확인)

- `POST /auth/logout` 컨트롤러: **존재** (`apps/api/src/modules/auth/presentation/controllers/auth.controller.ts` L83–94)
- `LogoutUseCase`: **구현됨** (`apps/api/src/modules/auth/application/use-cases/logout.use-case.ts`)
  - 쿠키 `refresh_token` 값에서 `<tokenId>.<rawToken>` 파싱 → `deleteByIdAndUser(tokenId, userId)` 호출 → 해당 기기 세션만 삭제 (다른 기기 유지)
  - `res.clearCookie('refresh_token', ...)` 로 쿠키 제거
- `RefreshToken` 엔티티: `{ id, userId, tokenHash, expiresAt }` — DB에 bcrypt 해시로 저장
- `TokenService.issueRefreshToken`: 쿠키 포맷 `"<db-id>.<rawToken>"`, HttpOnly · Secure · SameSite=strict · maxAge=14d
- 글로벌 prefix 없음 — 실 경로 `/auth/logout` (MSW mock 경로 `/api/v1/...`와 다름)

### FE 구현 현황 (직접 확인)

- 로그아웃 버튼: `apps/web/src/app/(user)/my/page.tsx`에 없음. 마이페이지 메뉴 항목으로 추가 필요
- 기존 유사 구현 (`MyPageHub.tsx`): 파일 미존재 — `localStorage.removeItem('accessToken')` 후 `router.push('/login')` 만 하는 코드는 **아직 미구현 상태** (사용자 제공 정보 기반)
- 토큰 관리: `apps/web/src/shared/api/auth-token.ts` — `localStorage('accessToken')` 단일 getter. `setAuthTokenGetter`로 교체 가능
- auth store/context: 없음

- Open decisions:
  - **D-1** 로그아웃 버튼 위치: 현재 `/my` 페이지(`MenuTable` rows)에 추가하는가, 별도 "프로필 설정" 페이지에 두는가? → 기능명세 연관화면 "마이페이지"이므로 `/my/page.tsx` MenuTable 말미에 추가하는 것을 기본 방향으로 잡되, 최종 확정은 디자인 시안 기준으로 결정
  - **D-2** 로그아웃 실패 처리 방식: `POST /auth/logout` 401(이미 만료된 세션) 응답 시 — 에러를 무시하고 클라이언트 토큰만 지우고 `/login`으로 이동할 것인가, 에러 토스트를 띄울 것인가?
  - **D-3** API 명세 응답 envelope(`statusCode / timestamp / path / message / data / error`)가 실제 BE 응답과 일치하는지 확인 필요. 현재 `auth.controller.ts`는 `void` 반환이므로 실 응답 body가 빈 `204` 또는 `{}`일 가능성 있음 → FE 연동 전 실제 응답 확인 필요 (HTTP status 200 vs 204, body 유무)

## API Contract (스냅샷)

> 출처: Notion API명세 DB `5852ee66b06c838bb8ec01c6bf4f2e25`, `/auth/logout` + 실 BE 코드 교차 확인

### 데이터모델

refresh token은 DB 테이블 `refresh_tokens`에 저장되며 쿠키 포맷 `"<id>.<rawToken>"`(HttpOnly)으로 전달된다.

```
RefreshToken {
  id:         string   // UUID, DB PK, 쿠키 앞부분
  userId:     string
  tokenHash:  string   // bcrypt hash of rawToken
  expiresAt:  Date     // 발급 시점 + 14일
}
```

### 엔드포인트

#### `POST /auth/logout`

**요청**

| 항목 | 값 |
|------|-----|
| 인증 | `Authorization: Bearer {accessToken}` (AuthGuard 적용) |
| 쿠키 | `refresh_token=<id>.<rawToken>` (HttpOnly, 없어도 에러 없음 — UseCase가 undefined 처리) |
| Body | 없음 |

**응답 (명세)**

| 상태 | Body |
|------|------|
| `200 OK` | `{ statusCode: 200, message: "로그아웃이 성공적으로 완료되었습니다.", data: null, error: null }` |
| `401 Unauthorized` | `{ statusCode: 401, message: "로그인 정보가 없거나 이미 만료된 세션입니다.", data: null, error: "UNAUTHORIZED" }` |
| `500 Internal Server Error` | `{ statusCode: 500, message: "로그아웃 처리 중 서버 오류가 발생했습니다.", data: null, error: "INTERNAL_SERVER_ERROR" }` |

**Set-Cookie (응답 헤더)**

```
Set-Cookie: refresh_token=; Max-Age=0; Path=/; HttpOnly; Secure; SameSite=Strict
```

> **주의 (D-3)**: `auth.controller.ts` `logout()` 메서드의 TypeScript 반환 타입은 `Promise<void>`. 실제 HTTP 응답이 `200 + 위 envelope body`인지 `200 + 빈 body`인지 실서버 호출로 교차 확인 필요. FE는 body 파싱 없이 `2xx` 여부만 판별해도 무방하도록 구현 권장.

## Scope

- In:
  - BE: `POST /auth/logout` 엔드포인트는 **구현 완료** — 별도 BE 작업 없음
  - FE: 마이페이지(`/my`)에 로그아웃 버튼 UI 추가
  - FE: 버튼 클릭 시 `POST /auth/logout` 호출 (accessToken 헤더 포함)
  - FE: 응답 성공(2xx) 시 `localStorage('accessToken')` 제거 후 `/login` 이동
  - FE: 응답 실패(401 등) 처리 — Open decision D-2 결정 후 구현

- Out:
  - 다른 기기 세션 전체 무효화 ("모든 기기에서 로그아웃") — 현재 BE UseCase는 현재 기기 단일 세션만 삭제. 전체 삭제 기능은 별도 기능으로 분리
  - access token 서버 측 블랙리스트 처리 — 현재 BE 미구현, JWT 만료(1시간)에 의존
  - 자동 로그인(remember me) 해제 — 기능명세 비고 언급이나 현재 자동 로그인 기능 미구현

## Plan

`POST /auth/logout`은 이미 구현 완료. 별도 BE 태스크 없음.

### FE

1. **API 함수 작성** (`apps/web/src/features/auth/logout/api.ts` 신규)
   - `logoutApi()`: `POST /auth/logout` 호출, `Authorization: Bearer <token>` 헤더 부착
   - `shared/api/auth-token.ts`의 `getAuthToken()` 사용

   - `finally` 블록에서 `localStorage.removeItem('accessToken')` 처리

   - `router.push('/login')` 이동
   - D-2 결정에 따라 에러 처리 분기 추가

   - UI: DESIGN.md 준수 (MenuTable 컴포넌트 기존 variant 그대로 사용)

4. **MSW mock 등록** (연동 전 개발/테스트용)
   - `POST /api/v1/auth/logout` → `200` 응답 핸들러

5. **실 API 연동 전환**
   - MSW mock 제거 또는 조건부 분기
   - D-3: 실 응답 envelope 확인 후 body 파싱 코드 조정

## Out (단계별 완료물)

- API: `POST /auth/logout` — 이미 구현 (`apps/api/src/modules/auth/presentation/controllers/auth.controller.ts`, `apps/api/src/modules/auth/application/use-cases/logout.use-case.ts`)
- UI: `apps/web/src/app/(user)/my/page.tsx` 로그아웃 항목 추가, `apps/web/src/features/auth/logout/` 디렉터리
- 연동: `getAuthToken()` → `Authorization` 헤더 → `POST /auth/logout` → `localStorage` 제거 → `/login` 리다이렉트

## Risks

- access token이 만료 전까지 서버 측에서 무효화되지 않음 (JWT 무상태 특성). 로그아웃 후 탈취된 access token(유효기간 최대 1시간)은 재사용 가능 — MVP 범위로 허용, 블랙리스트는 Out of scope
- `refresh_token` 쿠키가 없는 상태에서 `POST /auth/logout` 호출 시 UseCase가 쿠키 삭제만 하고 DB 삭제를 건너뜀 — 정상 동작이나 쿠키 없는 경우 silent fail임을 FE에서 인식해야 함
- `localStorage` 직접 의존: SSR 환경에서 `typeof window === 'undefined'` guard 필요 (`auth-token.ts`에 이미 존재하나 `removeItem` 호출 시점에도 guard 적용 필요)

## Validation

- Tests:
  - BE: `LogoutUseCase` 단위 테스트 — 쿠키 있을 때 `deleteByIdAndUser` 호출 여부, 쿠키 없을 때 DB 호출 없음 여부
  - FE: 로그아웃 훅 단위 테스트 — API 성공/실패 분기, `localStorage.removeItem` 호출, `router.push('/login')` 호출
- Manual checks:
  - 로그아웃 후 `/my` 접근 시 `/login` 리다이렉트 확인
  - DB `refresh_tokens` 테이블에서 해당 레코드 삭제 확인
  - 응답 헤더 `Set-Cookie: refresh_token=; Max-Age=0` 확인
  - 로그아웃 후 로그인 → 재로그아웃 정상 동작 확인
- Observability:
  - 401 응답 빈도 모니터링 (이미 만료된 세션에서의 로그아웃 시도)

## Decision Log

- D-1: 로그아웃 버튼 위치 — 기능명세 연관화면 "마이페이지". `/my/page.tsx` MenuTable 말미 기본 방향. 디자인 시안 확정 후 위치 결정.
- D-2: 로그아웃 API 실패 시 클라이언트 처리 — `finally`에서 무조건 토큰 제거 + 이동이 UX상 안전. 에러 토스트 노출 여부 결정 필요.
- D-3: 실 BE 응답 envelope 형태 교차 확인 — `void` 반환이므로 body 없을 수 있음. FE는 2xx 여부만 판별 권장.
