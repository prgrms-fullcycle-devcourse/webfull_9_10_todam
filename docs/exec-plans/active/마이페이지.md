### 엔드포인트

#### 1) `GET /users/me` — 내 프로필 조회 (정본)

마이페이지 진입 시 호출. 본인 계정 정보 반환.

**Headers:** `Accept: application/json`, `Authorization: Bearer {accessToken}`
**Request:** 없음 (토큰으로 userId 식별).

**시스템 처리:**
1. AuthGuard로 토큰 검증, payload `userId` 추출. 미인증 401.
2. `users`에서 userId 조회. `status=ACTIVE` 검증 — 탈퇴/비존재 시 404 `USER_NOT_FOUND`.
3. `userId, email, nickname, isPartner, createdAt` 패키징 반환.

**200 OK (정본 그대로 — `data` 본문):**
```json
{
  "user": {
    "userId": "eb50a73f-785f-49ce-887b-5f0bba67a1e3",
    "email": "user@example.com",
    "nickname": "토담이",
    "isPartner": false,
    "createdAt": "2026-05-24T16:55:00.000Z"
  }
}
```
> 공통 봉투 `{ statusCode, timestamp, path, message, data, error }`의 `data`에 위 객체. FE `apiFetch<T>`가 `data`만 언래핑.
> **사용처(UI 기준):** 정본 응답 그대로 사용. 허브에선 `isPartner`만 필요(파트너센터 노출, D8). 이메일·닉네임 표시는 **개인 정보 수정 sub-page**에서. 기능명세의 "한 화면 합성 조회"는 Figma 화면 구조와 불일치 → UI 기준으로 합성 안 함(D1 해소).

| 필드 | 타입 | 비고 |
|---|---|---|
| `userId` | `string(uuid)` | |
| `email` | `string` | 수정 불가(기능명세·비고) |
| `nickname` | `string` | |
| `isPartner` | `boolean` | Partner APPROVED 여부 |
| `createdAt` | `string(ISO)` | |

**에러:**

| status | code | message |
|---|---|---|
| 401 | `UNAUTHORIZED` | "인증 정보가 유효하지 않거나 만료되었습니다." |
| 404 | `USER_NOT_FOUND` | "존재하지 않거나 탈퇴 처리된 회원입니다." |
| 500 | `INTERNAL_SERVER_ERROR` | "프로필 조회 처리 중 서버 내부 오류가 발생했습니다." |

#### 2) `PATCH /users/me` — 내 프로필 수정 (정본)

개인정보 수정 화면 저장 버튼. 정본은 **닉네임만** 수정 대상.

**Headers:** `Content-Type: application/json`, `Accept: application/json`, `Authorization: Bearer {accessToken}`
**Request body (정본 그대로):**
```json
{ "nickname": "새로운토담이" }
```

**시스템 처리:**
1. AuthGuard 토큰 검증, userId 추출.
2. `nickname` 정책 검증: **공백 제외 2~10자, 특수문자 불가**(정본). → 위반 400 `INVALID_REQUEST`.
3. `users` 전체에서 닉네임 중복 조회 → 존재 시 409 `NICKNAME_ALREADY_EXISTS`.
4. `nickname` 갱신, `updatedAt = now()`. 최신 user 반환.

**200 OK (정본 그대로 — `data` 본문):**
```json
{
  "user": {
    "userId": "eb50a73f-785f-49ce-887b-5f0bba67a1e3",
    "email": "user@example.com",
    "nickname": "새로운토담이",
    "isPartner": false,
    "updatedAt": "2026-05-24T18:10:00.000Z"
  }
}
```
> **주의(D2):** 기능명세 "내 정보 수정"은 닉네임 + 예약자 이름 + 예약자 연락처 수정을 기대하나, 정본 요청·응답에 예약자 필드 없음. 예약자 정보 수정 경로 미정.

**에러:**

| status | code | message |
|---|---|---|
| 400 | `INVALID_REQUEST` | "닉네임은 특수문자를 제외한 2자 이상 10자 이내여야 합니다." |
| 401 | `UNAUTHORIZED` | "인증 정보가 유효하지 않거나 만료되었습니다." |
| 409 | `NICKNAME_ALREADY_EXISTS` | "이미 사용 중인 닉네임입니다. 다른 닉네임을 입력해주세요." |
| 500 | `INTERNAL_SERVER_ERROR` | "프로필 정보 수정 처리 중 서버 내부 오류가 발생했습니다." |

### zod contract 제안 (`packages/shared/src/contracts/user-me.ts` 신설, `index.ts` re-export)

```ts
// 정본(API명세) 기준. 예약자 필드는 D2 확정 전까지 미포함.
import { z } from 'zod';

export const userProfileSchema = z.object({
  userId: z.string().uuid(),
  email: z.string().email(),
  nickname: z.string(),
  isPartner: z.boolean(),
  createdAt: z.string().datetime().optional(), // GET 응답
  updatedAt: z.string().datetime().optional(), // PATCH 응답
});
export type UserProfile = z.infer<typeof userProfileSchema>;

export const getMyProfileResponseSchema = z.object({ user: userProfileSchema });

// 닉네임 정책: 공백 제외 2~10자, 특수문자 불가 (정본). 정규식 D5에서 확정.
export const updateMyProfileBodySchema = z.object({
  nickname: z.string().trim().min(2).max(10), // .regex(...) D5
});
export type UpdateMyProfileBody = z.infer<typeof updateMyProfileBodySchema>;

export const updateMyProfileResponseSchema = z.object({ user: userProfileSchema });

export const notificationSettingsSchema = z.object({
  id: z.string(),
  userId: z.string().uuid(),
  inAppEnabled: z.boolean(),
  emailEnabled: z.boolean(),
  kakaoEnabled: z.boolean(),
  reservationEnabled: z.boolean(),
  artworkEnabled: z.boolean(),
  shippingEnabled: z.boolean(),
  marketingEnabled: z.boolean(),
  updatedAt: z.string().datetime(),
});
export const getNotificationSettingsResponseSchema = z.object({
  notificationSettings: notificationSettingsSchema,
});
```

## Open decisions (사람 결정 대기 — 추측 금지)

- **D1. 마이페이지 합성 방식**: ✅ **해소(UI 기준)** — Figma 허브는 프로필/예약자/찜개수를 모아 표시하지 않음(내비 링크 + 알림 토글뿐). 합성 불필요. 허브는 `GET /users/me`(isPartner) + `GET /users/me/notification-settings`만. 기능명세의 "한 화면 통합 조회"는 화면 분할 구조와 불일치 → UI 정본.
- **D2. 예약자 정보(이름·연락처)**: ✅ **MVP 제외(UI 기준)** — 마이 허브·고객지원 어디에도 예약자 정보 표시/수정 UI 없음. 정본 `/users/me`에도 필드 없음. 개인정보 수정 sub-page 프레임 확보 시 재검토. 그 전까지 Out.
- **D3. 찜 공방 "개수" 표기**: ✅ **해소(UI 기준)** — UI는 "찜한 공방 목록" 링크만, 개수 숫자 없음. count 산출/필드 불필요. favorite-stores 본 화면 호출 안 함.
- **D4. 알림 설정 표시 범위**: ✅ **확정(Figma)** — inline 토글 2개(`artworkEnabled`/`marketingEnabled`)를 마이페이지에서 직접 on/off. → `PATCH /users/me/notification-settings` 본 plan 포함. (남은 확인: 토글 2개만 노출인지, 나머지 채널은 알림 plan 소관인지 — D6 모듈 소유권과 연계.)
- **D5. 닉네임 정규식 SSOT**: 정본은 "특수문자 제외 2~10자". 허용 문자(한글·영문·숫자 범위), 공백 정책(trim), 자모 단독 허용 여부 등 정확한 정규식을 zod에 고정하려면 명세 확정 필요. 회원가입 plan(`이메일-회원가입.md`)의 닉네임 규칙과 일치 여부도 교차 확인.
- **D6. notification-settings 모듈 소유권**: GET notification-settings를 마이페이지(users 모듈)에서 호출하나, 구현·소유는 알림 도메인 plan과 중복. 어느 plan이 BE를 소유하는지 확정(중복 구현 방지).
- **D7. DESIGN.md 작업 시작 조건**: ✅ **허브 해소(Figma 8505:19320)** — 토큰 위 UI 구조 섹션 참조. 남은 미확보: **개인 정보 수정(`PATCH`) 폼 화면** 디자인(입력 필드·저장 버튼 상태별 토큰). 해당 sub-page 프레임 필요.
- **D8. `파트너 센터 이동하기` 노출 조건·목적지**: `isPartner=true`만 노출인지, 항상 노출인지. 이동 목적지(파트너 도메인 라우트/외부 URL) 미정.
- **D9. 비밀번호 재설정·회원 탈퇴 진입점 위치**: Figma "마이" 프레임에 두 진입점 없음(고객지원에 로그아웃만). 기능명세/요구사항(auth §6 회원탈퇴)은 존재 → 별도 화면(예: 개인 정보 수정 하위)인지, 본 MVP 제외인지 확정 필요. **결정 전까지 두 진입점 본 화면 Out.**
