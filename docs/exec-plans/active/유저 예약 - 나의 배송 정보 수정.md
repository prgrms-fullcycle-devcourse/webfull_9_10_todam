### Open decisions

1. **잠금 기준 enum 표기 (D1)** — `Reservation.status ∈ {SHIPPED, DELIVERED}` 인지 `Artwork.status = COMPLETED` 이후 인지. **권장**: `Reservation.status` 기준 (requirements.md §8 흐름과 정합. SHIPPED·DELIVERED 둘 다 `ReservationStatus`에만 존재). 정본 갱신 필요 — BE 답변 대기.
2. **401 분기 (D2)** — 공통 AuthGuard 기준 `401 UNAUTHORIZED` 보정. 정본 갱신 후 본 contract 재고정.
3. **404 분기 (D3)** — `404 RESERVATION_NOT_FOUND` 보정. 정본 갱신 후 본 contract 재고정.
4. **연락처 정규식 (D4)** — `PHONE_REGEX = /^010-\d{4}-\d{4}$/` (휴대폰 전용) 채택 권장. 정본 미명시 — BE/FE 합의 필요. (대안: `STORE_PHONE_REGEX` 유선 허용 — 권장 안 함)
5. **응답 `delivery.id` 노출 (D5)** — MVP 범위 외. 후속 endpoint에서 필요 시 별도 결정.
6. **수정 이력 정책 (D8)** — MVP 범위 외. 후속 plan으로 분리.

### 엔드포인트

`PATCH /reservations/{reservationId}/delivery` — 인증된 User가 본인 예약(택배)의 배송 정보를 등록·수정한다.

**Headers (정본 그대로):**
- `Content-Type: application/json`
- `Accept: application/json`
- `Authorization: Bearer {accessToken}`

**Path Parameters:**
- `reservationId: string(uuid)` — 예약 UUID

**Query Parameters:** 없음.

**Request Body (정본 그대로):**

```json
{
  "recipientName": "김리듬",
  "recipientPhone": "010-9876-5432",
  "postalCode": "04001",
  "address": "서울특별시 마포구 월드컵북로 12",
  "addressDetail": "101호"
}
```

| 필드 | 타입 | 검증 | 비고 |
|---|---|---|---|
| `recipientName` | `string` | 필수, 1~100자 (`Delivery.recipientName` 컬럼 길이) | 정본 "필수 정보를 입력하지 않으면 저장할 수 없다" |
| `recipientPhone` | `string` | 필수, **`PHONE_REGEX = /^010-\d{4}-\d{4}$/`** (D4 결정 권장) | 정본 "연락처 형식이 올바르지 않으면 저장할 수 없다" |
| `postalCode` | `string` | 필수, `/^\d{4,6}$/` (한국 5자리 우편번호. Daum 응답 zonecode 길이 변동 보정) | 정본 "주소 정보를 입력하지 않으면 저장할 수 없다" |
| `address` | `string` | 필수, 1~500자 | 정본 동일. 저장 시 `Delivery.shippingAddress` 로 매핑 (D6) |
| `addressDetail` | `string` | 선택?/필수? 정본 모호. **권장: 필수 1~200자** (Delivery 컬럼 200자 한도) | 정본 "필수 정보를 입력하지 않으면" 의 범주 — BE/FE 합의 필요 |

**시스템 처리 (정본 그대로):**
1. 인증 토큰으로 사용자 식별 (AuthGuard) — 미인증 시 401 (D2 보정).
2. `reservationId` 로 예약 조회 + 소유자 검증. 비존재 시 404 (D3 보정). `Reservation.userId !== currentUserId` 시 403 FORBIDDEN.
3. `Reservation.deliveryMethod === 'DELIVERY'` 확인. `PICKUP` 이면 **409 PICKUP_NOT_ALLOWED** ("픽업 예약은 배송 정보를 수정할 수 없습니다."). (정본 에러 코드 목록엔 명시 없지만 정본 처리 단계 "PICKUP_NOT_ALLOWED"로 적시 — Open decision으로 별도 박지 않음. 다만 응답 봉투 에러 코드 list에 추가 필요)
4. 잠금 기준 검증(D1 결정 후 확정): `Reservation.status ∈ {SHIPPED, DELIVERED}` 또는 `Artwork.status ∈ {COMPLETED, ?}` 이면 **409 DELIVERY_NOT_EDITABLE** ("이미 발송된 작품의 배송 정보는 수정할 수 없습니다.").
5. `recipientName`/`recipientPhone`/`postalCode`/`address` 필수값 + 형식 검증. 위반 시 **400 DELIVERY_INFO_INVALID**.
6. `deliveries` 테이블 upsert (where `reservationId`): `recipientName`/`recipientPhone`/`postalCode`/`shippingAddress(=address)`/`addressDetail` 5필드 갱신. `trackingNumber`/`carrier`/`shippedAt`는 건드리지 않음. `updatedAt` 갱신.
7. 저장된 배송 정보 직렬화 반환.

## UI 동작 흐름 (정본 기능명세 기반)

1. **진입 (`DeliveryInfoSection.tsx`)**
   - `delivery == null || !delivery.address` → 빈 상태 카드의 **"배송지 입력하기"** 버튼 노출. onClick: 배송 정보 시트 open (mode = `create`).
   - `delivery && delivery.address` → 입력됨 카드 헤더의 **"수정하기"** 버튼 노출. onClick: 배송 정보 시트 open (mode = `edit`, 기존 값 prefill).
   - 본 plan에서 이 두 핸들러를 placeholder 토스트 → 실제 시트 트리거로 교체.
2. **시트 콘텐츠 (`DeliveryEditSheet`)**
   - 헤더: "배송 정보 입력" / "배송 정보 수정"
   - 필드 5개 (react-hook-form + zod):
     - `recipientName` text input
     - `recipientPhone` text input (auto-hyphen 적용 검토 — D4 후)
     - `postalCode` input (readonly, disabled) + **"주소 찾기" 버튼** → `openPostcode()` 호출 → 결과로 `postalCode` + `address` 동시 set
     - `address` input (readonly, disabled) — 주소 찾기 결과 자동 채움
     - `addressDetail` text input (사용자 입력)
   - 하단 CTA: "저장" (filled primary) — 미충족 시 disable. "취소" (ghost) — 시트 close.
3. **저장 처리**
   - 저장 클릭 → 폼 zod 검증 통과 → `PATCH /reservations/{id}/delivery` 호출
   - 200 OK → 토스트 "배송 정보가 저장되었어요" + 예약 상세 캐시 무효화 + 시트 close
   - 400 → 폼 필드 에러로 매핑 (BE 에러가 어느 필드인지 명시되지 않으면 전역 에러 텍스트)
   - 409 PICKUP_NOT_ALLOWED → 토스트 "픽업 예약은 배송 정보 수정 불가" + 시트 close (이 경우 본래 빈 상태 카드가 노출되지 말아야 함 — `deliveryMethod === DELIVERY` 가드를 진입점에서 한 번 더 확인)
   - 409 DELIVERY_NOT_EDITABLE → 토스트 "이미 발송된 작품은 수정 불가" + 시트 close + 캐시 무효화(상태 변화 반영)
   - 401 → 로그인 리다이렉트 (전역 핸들러)
   - 403/404 → 토스트 + 상세 화면 캐시 무효화 (잘못된 진입)
   - 500 → 토스트 "잠시 후 다시 시도해주세요" + 시트 유지 (재시도 가능)
4. **빈 상태 가드** (진입점 추가 검증)
   - `reservation.deliveryMethod !== 'DELIVERY'` → 본 섹션 자체 미노출 (현재 `DeliveryInfoSection`은 `deliveryMethod` 분기가 없음 — 부모 페이지에서 분기 중인지 확인 필요). 본 plan에서 부모 페이지 분기 추가 또는 컴포넌트 내부 가드 추가.

## Risks

- **drift 9건 중 D1(잠금 기준 enum 표기)이 가장 결정적** — `Reservation.status` 인지 `Artwork.status` 인지 정해지지 않으면 BE 가드 작성 불가. **정본 갱신 선결정 필수.** (현재 ArtworkStatus enum에 SHIPPED/SHIPPING 없으니 Reservation.status 잠금이 자연스러우나, 정본이 그렇게 적혀있으니 BE에 명시 확인 필요.)
- **D4 연락처 정규식 미확정** — 휴대폰만(권장) vs 유선 허용 결정 없이는 shared zod 스키마 + BE 검증 둘 다 멈춤.
- ~~**Figma 정본 미확보** → FE 폼 UI 착수 불가.~~ **해소(2026-06-02)** — §Design tokens 신설. FE 폼 UI 착수 가능 (D1·D4 BE 결정만 의존).

- **부모 컴포넌트 가드 누락 가능성** — `DeliveryInfoSection` 자체는 `deliveryMethod` 분기가 없음. 부모(`ReservationDetailClient`)에서 분기 중이라고 가정하지만 확인 필요. 만약 미분기면 PICKUP 예약에도 빈 상태 카드("배송지 입력하기")가 노출되어 사용자 혼란 → 진입점 가드 추가 필요.
- **upsert 동시성** — 동일 사용자가 두 탭에서 동시에 저장 시 last-write-wins. 디자인이 conflict UI 안 잡혀 있으면 이대로 둠. (D8 관련 후속 정책)
- **주소검색 zonecode 길이 변동** — Daum 응답이 5자리지만 과거 6자리 우편번호 호환을 위해 zod `/^\d{4,6}$/` 권장. 정본은 예시 `04001`(5자리).
- **응답 봉투의 `delivery` 객체 ≠ 예약 상세 응답의 `delivery` 객체** — 본 endpoint 응답은 5필드만, 예약 상세 응답은 7필드(+`carrier`/`trackingNumber`). FE 캐시 머지 시 둘을 혼동하지 않도록 mapper 또는 별도 타입 사용.
