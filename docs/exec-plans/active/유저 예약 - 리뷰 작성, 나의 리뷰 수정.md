# Feature Plan: 유저 예약 - 리뷰 작성, 나의 리뷰 수정 (user / review)

## Summary

- Goal: 인증된 User 가 본인 예약(체험 완료, `IN_PROGRESS` 이상)에 대해 **리뷰를 신규 작성**하고, 본인이 작성한 리뷰를 **수정**한다. 별점(필수) + 본문(선택, ≤500자) + 사진(선택, ≤3장·1장 5MB) 입력. 사진은 presigned → S3 PUT → 최종 작성/수정 요청 바디에 S3 Key 목록(`photos: string[]`) 일괄 제출. 작성 완료/수정 완료 시 예약 상세 + 리뷰 데이터 invalidate. 2 기능을 review 도메인 user side **write** 트랙으로 묶음.

- **photos 처리 (D14/D15 갭 브리지) — RESOLVED**: POST/PATCH 의 `photos: string[]` 각 항목 — **`http`로 시작(전체 URL)이면 기존 유지분 → imageUrl 그대로 저장**, 아니면 **S3 key → imageUrl=`${CDN_BASE}/${key}`**. - **D16(Content-Type json) / D15(PATCH shape) / D18(수정이력 미신설)** — 계약/코드대로 확정. 썸네일·통계 갱신 = **defer**(워커 없음 / read 시 계산).

**확정 BE 처리**:
- `POST /reservations/{reservationId}/review`: AuthGuard → ① 예약 조회 없음 404 `RESERVATION_NOT_FOUND` ② `reservation.userId≠요청자` 403 `FORBIDDEN` ③ 상태 미허용 400 `REVIEW_NOT_ALLOWED` ④ `scheduledAt`+180일 초과 400 `REVIEW_DEADLINE_EXCEEDED` ⑤ 기존 Review(reservation unique) 있으면 409 `REVIEW_ALREADY_EXISTS` ⑥ 트랜잭션: Review 생성(rating, content, storeId=reservation.storeId) + ReviewPhoto 일괄. → 201 `data.review = reviewDetailSchema`(photos `{id, imageUrl}` sortOrder ASC, content ?? '').
- `PATCH /reviews/{reviewId}`: AuthGuard → ① 없음 404 `REVIEW_NOT_FOUND` ② `review.userId≠요청자` 403 `FORBIDDEN` ③ `createdAt`+30일 초과 400 `REVIEW_EDIT_DEADLINE_EXCEEDED` ④ 트랜잭션: rating·content 갱신 + review_photos 전량 삭제 후 재생성. → 200 `data.review = reviewUpdateResponseSchema`(`{id, rating, content ?? '', photos: imageUrl[], updatedAt}`).
- `POST /review/images/presigned`: AuthGuard → key=buildObjectKey(`reviews/photos`, fileType, fileName), uploadUrl=presign(key,fileType,300). → **201**(store presigned 라우트 `@ApiCreatedResponse` 컨벤션 일치 — 원래 200 적었으나 임의값이라 코드베이스 컨벤션으로 정정, FE 는 2xx 무관) `data = { uploadUrl, key }`.
- DTO 전부 `createZodDto`(shared schema). 요청 검증 `BodyZodValidationPipe`(작성/수정=reviewWriteRequestSchema, presigned=reviewImageUploadRequestSchema). `@ResponseMessage` 계약 메시지.

**모듈 배치** = 신규 `apps/api/src/modules/review/`: controller(3 라우트) + use-cases(create-review/update-review/issue-review-image-presigned) + domain repository(abstract) + prisma repository + module(S3Module import). `app.module.ts` 등록. **이번 batch 범위 = BE 3개만**(FE 완료·핸드오프). shared `ReviewWriteErrorCode` 에 `REVIEW_NOT_ALLOWED` additive 추가.

### Drift 점검 (Notion 정본 ↔ 본 plan 채택)

**작성 (기능명세 1 / API명세 1)** — 본문·API 정본 일치. POST 응답 shape 명확(`photos: [{id, imageUrl}]` + `createdAt`). 비고에 "수정 가능 여부 정책"(D17) 미정.

**presigned (API명세 3)** — **본문 전체 빈 값.** 메서드+URI 만 존재. 가장 큰 drift(D14). store/program presigned 패턴 SSOT 격상 여부 BE/메인 결정 필요.

### 엔드포인트 A — 리뷰 작성

`POST /reservations/{reservationId}/review` — 인증 사용자 본인 예약의 리뷰 신규 작성. (API명세 1 정본 그대로.)

**Headers:** `Content-Type: application/json`, `Accept: application/json`, `Authorization: Bearer {accessToken}`

**Path Parameters:**
- `reservationId: string(uuid)`

**Request Body (정본 그대로):**
```json
{
  "rating": 5,
  "content": "정말 즐거운 체험이었어요.",
  "photos": ["reviews/photos/uuid-..._review_photo.jpg"]
}
```

| 필드 | 타입 | 필수 | 비고 |
|---|---|---|---|
| `rating` | `number(1~5)` | ✅ | 별점 미입력 시 등록 불가 |
| `content` | `string(≤500)` | 선택 | 요구사항 §2 최대 500자 |
| `photos` | `string[](≤3)` | 선택 | **S3 Key 목록**(presigned 선행 업로드 완료분). 1장당 5MB·JPG/PNG/HEIC |

**시스템 처리 (정본 그대로):**
1. 토큰 식별(AuthGuard).
2. 예약 소유자 검증 — 미일치 `403 FORBIDDEN`. 비존재 `404 RESERVATION_NOT_FOUND`.
3. 상태 `IN_PROGRESS` 이상 검증.
4. `IN_PROGRESS` 도달 시점부터 180일 이내 + 기존 리뷰 없음 — 초과 `400 REVIEW_DEADLINE_EXCEEDED`, 중복 `409 REVIEW_ALREADY_EXISTS`.
5. `reviews` 레코드 생성(rating, content).
6. `photos` S3 Key 배열 순회 → `review_photos` 일괄 삽입(sortOrder).
7. BullMQ 비동기 썸네일·최적화.
8. 공방·프로그램 평균 별점·리뷰 수 실시간 갱신.
9. 응답.

**응답 201 Created — 공통 봉투 (정본 그대로):**
```json
{
  "statusCode": 201,
  "timestamp": "2026-06-02T10:00:00.000Z",
  "path": "/reservations/res-uuid-001/review",
  "message": "리뷰가 성공적으로 등록되었습니다.",
  "data": {
    "review": {
      "id": "review-uuid-001",
      "reservationId": "res-uuid-001",
      "rating": 5,
      "content": "정말 즐거운 체험이었어요.",
      "photos": [
        { "id": "photo-uuid-001", "imageUrl": "https://cdn.todam.app/reviews/.../001.jpg" }
      ],
      "createdAt": "2026-06-02T10:00:00.000Z"
    }
  },
  "error": null
}
```

**data.review 스키마 — `reviewDetailSchema`(`reservation-detail.ts` L89~108) 재사용 가능** (POST 응답 = GET 응답과 동일 shape).

| 필드 | 타입 | 출처 |
|---|---|---|
| `id` | `string(uuid)` | `Review.id` |
| `reservationId` | `string(uuid)` | `Review.reservationId` |
| `rating` | `number(1~5)` | `Review.rating` |
| `content` | `string` | `Review.content` (null → 빈 문자열) |

**에러 (정본 그대로):**

| 401 | `UNAUTHORIZED` | "인증 정보가 유효하지 않거나 만료되었습니다." |

### 엔드포인트 C — 리뷰 사진 업로드 (presigned) — **정본 부재 (D14)**

`POST /review/images/presigned` — 리뷰 사진 S3 presigned URL 발급. **Notion API명세 본문 전체 빈 값.** 아래는 store/program presigned 패턴 기반 **추론 contract (BE 확정 전 미고정)**.

**Headers:** `Content-Type: application/json`, `Accept: application/json`, `Authorization: Bearer {accessToken}`

**Request Body (추론 — program-edit 패턴):**
```json
{ "fileName": "review.jpg", "fileType": "image/jpeg" }
```

**응답 (추론 — D14 핵심 결정 포인트):**
```json
{
  "data": {
    "uploadUrl": "https://s3.../presigned-put-url",
    "key": "reviews/photos/uuid-..._review_photo.jpg"
  }
}
```

> **D14 — BE 확정 필수:** presigned 응답에 **S3 `key`** 가 반드시 포함되어야 함. POST/PATCH review 의 `photos: string[]` 는 **S3 Key** 를 수용하는데, program presigned 응답은 `imageUrl`(URL)만 반환(`programImageUploadResultSchema`). 리뷰는 key 단위 → 응답 contract 가 다름. **BE 가 명세 본문 채울 때까지 contract 미확정.** FE 업로드 흐름: ① `POST /review/images/presigned` → ② `uploadToS3(uploadUrl, file)`(PUT, Authorization 제외 — `program/edit/api.ts` L55~64 재사용) → ③ 받은 `key` 들을 POST/PATCH `photos[]` 에 담아 제출.

## Risks

- **presigned 정본 완전 부재(D14).** 응답에 S3 `key` 미포함 시 POST/PATCH `photos[]` 바인딩 불가 → 사진 흐름 전체 블록. **최우선 BE 명세 확정.**
- **PATCH Content-Type 모순(D16).** multipart 확정 시 FE 업로더·body 직렬화 전면 재작성. S3 Key 방식과 모순 — BE 확인 전 json 가정 위험.
- **PATCH 응답 shape 불일치(D15).** FE 가 PATCH 응답에 직접 의존하면 photos URL/key·createdAt/updatedAt 정규화 버그. 본 plan 은 invalidate+GET 재조회로 회피하나 BE 통일이 근본 해결.
- **deadline 기준 시점 혼재(D22).** 작성 180일(IN_PROGRESS 도달) vs 수정 30일(API명세 "작성일" / 요구사항 "IN_PROGRESS 전이 후"). FE 가드(D13)는 `createdAt` 기준 — 요구사항과 어긋날 수 있음. BE 통일 + contract 에 기준 필드 명시 필요.
- **RatingInput 신설(D20).** 입력용 별점 컴포넌트 부재 → 신설. 접근성(키보드/aria)·hover 프리뷰·터치 hit target 고려. 디자인 토큰 의존.
- **FSD 레이어 배치(D25).** 팀 신규 합의로 폼/인터랙션은 `features/`, 표시 카드는 `entities/`, 페이지는 `app/`. 본 plan 신규 컴포넌트는 규칙 준수하되, 자매 #104·아트워크 #92 기존 `_components` 직배치 소급 재정렬은 이미 오픈된 PR 을 건드림 → 스코프·타이밍 사용자 확인 필요.
- **이탈 확인 모달(D24).** SPA route guard + `beforeunload` 조합 복잡. dirty 추적 누락 시 데이터 유실 또는 과도한 모달.
- **작성 중복(409)·예약당 1건.** ReviewSection 진입 가드 누락 시 작성 화면 재진입 → 409. hasReview·displayState 동기화 필수.
- **라우트 분리(D19) 확정 전 착수 시** 자매 plan 상세 라우트와 충돌. write/edit 경로 디자인 확정 필요.
