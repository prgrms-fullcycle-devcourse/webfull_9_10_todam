### Open decisions

**Figma 정본 4 변형(2026-06-01) 수신으로 D1~D6 방향 확정 — BE에서 contract 확장 결정만 남음.** (상세 토큰은 아래 §Design tokens 섹션 참조.)

1. **결제 금액 (D1)** — ✅ **확정**: 디자인 ResultTable에 "결제 90,000원" 표시. 응답에 결제 금액 필드 추가 필요. **BE 결정**: 필드명(`payment.totalPrice` vs `totalPrice` 평탄화) + 계산 위치(`programSnapshot.price × participantCount` BE 산출). 권장 `data.reservation.totalPrice: number`.
2. **배송 정보 확장 (D2)** — ✅ **확정**: 디자인 운송장 row가 (a) 미발송 시 "작품 배송이 시작되면 운송장 번호를 알려드릴게요" 빈 상태, (b) 발송 시 "우체국 택배 + 1111222233334 + 복사하기" 노출. 응답에 `delivery.carrier`, `delivery.trackingNumber`(둘 다 nullable) 추가 필요. **`trackingUrl` 불필요** — 디자인은 복사하기 패턴이라 carrier→URL 매핑 안 함.
3. **수령인 ↔ 예약자 동일성 (D3)** — ✅ **확정**: 디자인 배송 정보 ResultTable에 "김리듬 / 010-0000-0000 / 서울특별시 ..." 별도 표시 → 수령인은 예약자와 **별도 필드** 필요. 응답에 `delivery.recipientName`, `delivery.recipientPhone`, `delivery.address` 추가 필요(`shippingAddress`는 `delivery.address`로 명칭 일관). prisma `Delivery` 모델 확장 필요(현재 필드 부족할 수 있음 — BE 확인).
4. **리뷰 정보 소스 (D4)** — ✅ **확정**: 디자인 리뷰 섹션 별도 카드 (Rating + content + 썸네일). 본 응답엔 `hasReview: boolean` + `reviewId: string | null` 플래그만 두고 **상세는 별도 endpoint**(`GET /reservations/{id}/review` 또는 `GET /reviews/{id}`)로 분리. BE 결정만 남음.
5. **취소 가능 여부·시한 (D5)** — ✅ **확정**: 디자인 더보기 메뉴 "예약 취소하기" + dialog 2종 (가능: "예약을 취소할까요?" / 불가: "예약 취소가 마감되었어요. 체험 n일 전까지 가능"). 응답에 `canCancel: boolean` + `cancelDeadlineDays: number | null`(불가 dialog 메시지의 "n일" 채움용) 추가 필요. **BE 산출** — `Store.cancelDeadlineDays` + `scheduledAt`로 계산.
6. **작품 제작 단계 데이터 (D6)** — ✅ **부분 확정**: 디자인 작품 제작 단계 카드 = Badge(substate 라벨) + statusMessage + ProgressBar(현재 진척률 fill) + "완성까지 N단계 남음" + "자세히보기 >". 본 응답에 추가 필드 필요: `artwork.progressPercent: number`(progress bar fill용) + `artwork.remainingSteps: number`("N단계 남음"). 카드 자체는 본 응답으로 렌더, "자세히보기"는 **별도 endpoint + 별도 plan**(작품 §4 작품 제작 단계 조회)으로 분리.
7. **404 본문 typo (정본)** — `RESERVATION_NOT_FOUND`(message "예약을 찾을 수 없습니다.")로 보정 가정. 정본 갱신 후 contract 재고정.
8. **401 UNAUTHORIZED 분기** — 정본에 명시 없음. 공통 `AuthGuard` 기준 401(message "인증이 필요합니다.", error "UNAUTHORIZED")로 보정. 다른 인증 엔드포인트와 정합.
9. ~~**UI 작업 시작 조건(DESIGN.md)**~~ → **해소(2026-06-01)**: Figma 4 변형 수신 — 체험 전 / 체험 완료(리뷰 전) / 체험 완료(리뷰 후) / 취소 다이얼로그(가능·불가). 컨테이너/섹션/토큰/Modal·Menu·DescriptionBlock·ProgressBar·Rating·ReviewItem 등 컴포넌트 키 확보. FE 착수 가능.

### 데이터모델 (apps/api/prisma/schema.prisma 스냅샷)

`Reservation` (model `reservations`) — `/reservations/me` 와 동일. 핵심:

| 필드 | 타입 | 비고 |
|---|---|---|
| id | String @id uuid | path param |
| userId | String? uuid | null 은 source=PARTNER_MANUAL 만. 본 엔드포인트는 `userId === currentUserId` 가드 |
| programId / storeId / programTimeSlotId / programSnapshotId | uuid | 응답 storeName/programTitle/scheduledAt 등 source |
| scheduledAt | DateTime tz | 응답 `scheduledAt` |
| reserverName | String | 응답 `reserverName` |
| reserverPhone | String | 응답 `reserverPhone` |
| participantCount | Int @default(1) | 응답 `participantCount` |
| deliveryMethod | ReservationDeliveryMethod | DELIVERY \| PICKUP — 응답 `deliveryMethod` |
| status | ReservationStatus @default(PENDING) | 응답 `status` + displayState 산출 입력 |
| requestMemo | String? | 응답 `requestMemo` (정본 응답 예시에 포함) |
| internalMemo | String? | 응답 미노출 (파트너 전용) |
| source | ReservationSource | CUSTOMER \| PARTNER_MANUAL |
| canceledBy / cancelReason / canceledAt | String?/String?/DateTime? | 취소 메타 (응답 미노출, 또는 status=CANCELED 시 reason 노출 검토) |
| createdAt | DateTime @default(now()) | 응답 `createdAt` |

연관 (응답 산출에 필요):
- `program  Program` — `Program.title` → 응답 `programTitle`
- `store    Store` — `Store.name` → 응답 `storeName`, **`Store.cancelDeadlineDays`** → 취소 가능 시한 산출(D5)
- `programSnapshot ProgramSnapshot` — `price`/`capacity`/`leadTimeDays` 스냅샷. **응답 결제금액(D1) 산출용 `price × participantCount`**
- `artwork  Artwork?` — `Artwork.status` → IN_PROGRESS 구간 displayState 산출, `Artwork.id` → 응답 `artworkId`
- `delivery Delivery?` — `Delivery.shippingAddress` → 응답 `shippingAddress`(현 정본 포함), **`trackingNumber`/`carrier`/`shippedAt`** → 운송장 응답 확장(D2)
- `review   Review?` — `Review.id` → 응답 `reviewId` 또는 별도 endpoint(D4)

`enum ReservationStatus` (8): `PENDING`, `CONFIRMED`, `CANCELED`, `IN_PROGRESS`, `SHIPPED`, `DELIVERED`, `PICKUP_READY`, `PICKUP_DONE`
`enum ReservationDeliveryMethod`: `DELIVERY`, `PICKUP`
`enum ReservationSource`: `CUSTOMER`, `PARTNER_MANUAL`
`enum ArtworkStatus` (displayState 보조): `RESERVED`, `VISITED`, `DRYING`, `BISQUE_FIRING`, `GLAZING`, `GLAZE_FIRING`, `COMPLETED`, `CANCELED`

### 엔드포인트

`GET /reservations/{reservationId}` — 인증 사용자(Authorization: Bearer {accessToken}) 본인 예약 상세 1건.

**Headers:** `Accept: application/json`, `Authorization: Bearer {accessToken}`

**Path Parameters:**
- `reservationId: string(uuid)`

**Query Parameters:** 없음.

**시스템 처리:**
1. 토큰으로 사용자 식별 (AuthGuard)
2. `reservationId` 로 예약 조회. 비존재 시 `404 RESERVATION_NOT_FOUND`(Open decision 7).
3. `Reservation.userId === currentUserId` 검증. 미일치 시 `403 FORBIDDEN`. (PARTNER_MANUAL source 의 userId=null 도 비본인이므로 403)
4. `Reservation.status` + (IN_PROGRESS면 `Artwork.status`) 로 `displayState` 계산 — `packages/shared/src/constants/reservation-status-visual.ts` 와 정렬되는 displayState 매퍼(BE) 사용. 기존 plan(`user-예약-나의 예약조회.md`)의 매핑 표 그대로 재사용.
5. 응답 직렬화: 공통 봉투 + data.reservation.

**응답 200 OK — 공통 봉투 `{ statusCode, timestamp, path, message, data, error }` (정본 그대로):**

### displayState 계산 규칙 (선행 plan 재사용)

서버가 `Reservation.status`(+ IN_PROGRESS면 `Artwork.status`)로 **파생** 계산. 매핑 테이블은 선행 plan `docs/exec-plans/active/user-예약-나의 예약조회.md` 의 "displayState 정본 매핑" 표를 그대로 사용한다.

- `Reservation.status != IN_PROGRESS` → Reservation 상태 테이블 (8 status 중 7) — label/description, `subLabel = null`
- `Reservation.status == IN_PROGRESS` → Artwork 상태 테이블 — `label = "제작 중"`, `subLabel` = "건조"/"초벌"/"유약"/"재벌", `description` 매핑

본 plan은 매핑 SSOT를 변경하지 않는다. `RESERVATION_STATUS_VISUAL` (`packages/shared/src/constants/reservation-status-visual.ts`) 도 그대로 재사용.

## UI 동작 흐름 (정본 기능명세 기반)

1. **예약 기본 정보 영역**
   - 클래스명(`programTitle`), 공방명(`storeName`), 예약 날짜·시간(`scheduledAt`), 예약 인원(`participantCount`), 결제 금액(D1 후), 작품 수령 방식(`deliveryMethod` 라벨)
   - 예약 번호: `id` 노출 또는 가공된 단축 표시(정본 미규정 — 디자인 토큰 확인 필요)
2. **배송 정보 영역** (`deliveryMethod === 'DELIVERY'` 일 때만 노출)
   - 수령인 이름·연락처(D3 — 잠정 `reserverName`/`reserverPhone` 사용), 주소(`shippingAddress`)
   - 운송장 번호(D2 — `delivery.trackingNumber`) + 운송장 조회 링크(D2 — `delivery.trackingUrl`)
   - **MVP**: 운송장 번호 옆 "복사하기" 버튼만 제공 (외부 추적은 carrier별 외부 링크로 사용자가 직접 진입 — `requirements.md` §8.4)
   - 빈 상태: 배송 정보(특히 `trackingNumber`)가 아직 없으면 "운송장 정보 미입력" 빈 상태 카드. 디자인 토큰 대기.
3. **작품 제작 단계 영역**
   - `displayState.subLabel`(IN_PROGRESS 구간만) + `displayState.description` 노출
   - 상세 타임라인(단계별 사진/로그)은 본 plan 범위 외 — 별도 endpoint + 별도 plan(D6). 본 화면엔 "작품 제작 단계 보기" CTA만 두고 별도 라우트로 이동.
4. **리뷰 정보 영역**
   - `IN_PROGRESS` 이상 + 본인 작성 리뷰가 있을 때 노출 (D4 — 별도 endpoint 분리 가정)
   - 빈 상태: 작성 가능 조건 충족 시 "리뷰 작성" CTA, 미충족 시 안내 텍스트
5. **예약 취소 영역** (`status` ∈ `PENDING` | `CONFIRMED` + 본인 + 취소 가능 시한 이내일 때만 활성)
   - 활성 조건 계산: D5(BE 산출 `canCancel`) 결정 후 반영. 미결정 시 FE에서 `status` + `scheduledAt` + `Store.cancelDeadlineDays`로 산출(단, store 정보를 본 응답에 포함하지 않으면 별도 호출 필요 — D5에서 확정)
   - 취소 버튼 클릭 → 별도 `POST /reservations/{id}/cancel` (별도 plan 범위) — 본 plan은 버튼 노출/활성화 조건과 CTA 라우팅까지만.
