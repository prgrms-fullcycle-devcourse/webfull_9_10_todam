### 데이터모델 (apps/api/prisma/schema.prisma 스냅샷)

**스키마 준비 상태: 완비 (migration 불필요)**

`Reservation` — 취소 관련 필드:

| 필드 | 타입 | 비고 |
|---|---|---|
| `status` | `ReservationStatus` | `PENDING` / `CONFIRMED` → `CANCELED` 전이 |
| `canceledBy` | `String? @db.Uuid` | `User.id` (canceledByUser 관계) |
| `cancelReason` | `String?` | 취소 사유 자유 텍스트 |
| `canceledAt` | `DateTime? @db.Timestamptz(6)` | 취소 시각 |
| `source` | `ReservationSource` | `CUSTOMER` 인 경우에만 User 취소 대상 |
| `storeTimeSlotId` | `String @db.Uuid` | slot reservedCount 원복 대상 |
| `participantCount` | `Int` | decrement 수량 |

`StoreTimeSlot` — 취소 시 원복 대상:

| 필드 | 타입 | 비고 |
|---|---|---|
| `reservedCount` | `Int @default(0)` | 취소 시 `participantCount`만큼 decrement (floor 0) |

`Artwork` — 취소 시 전이 대상:

| 필드 | 타입 | 비고 |
|---|---|---|
| `status` | `ArtworkStatus` | `→ CANCELED` 전이 |
| `reservationId` | `String @unique` | reservation과 1:1 |

`QrToken` — Artwork와 1:1. 취소 시 별도 처리 없음. Artwork.status=CANCELED가 무효 신호로 동작(O4 확정).

`enum ReservationStatus`: `PENDING`, `CONFIRMED`, `CANCELED`, `IN_PROGRESS`, `SHIPPED`, `DELIVERED`, `PICKUP_READY`, `PICKUP_DONE`

`enum ReservationSource`: `CUSTOMER`, `PARTNER_MANUAL`

`enum ArtworkStatus`: `RESERVED`, `VISITED`, `DRYING`, `BISQUE_FIRING`, `GLAZING`, `GLAZE_FIRING`, `COMPLETED`, `CANCELED`

### 엔드포인트

`POST /reservations/{reservationId}/cancel` — 인증 사용자(Authorization: Bearer {accessToken}) 본인 예약 취소.

**Headers:** `Authorization: Bearer {accessToken}`, `Accept: application/json` (Content-Type 불필요 — 바디 없음)

**Path Parameters:**
- `reservationId: string(uuid)` — 취소할 예약 ID

**Request Body:** 없음 (바디 파싱 없음. cancelReason은 항상 null로 기록)

**시스템 처리:**
1. 토큰으로 사용자 식별 (AuthGuard)
2. `reservationId`로 예약 조회. 비존재 시 `404 RESERVATION_NOT_FOUND`.
3. `Reservation.userId === currentUserId` 검증. 미일치(또는 userId=null, 또는 source=PARTNER_MANUAL) 시 `403 FORBIDDEN`.
4. **상태 검증**: `status === CANCELED` → `409 ALREADY_CANCELED`. `status ∉ {PENDING, CONFIRMED}` → `409 INVALID_RESERVATION_STATUS`.
5. **취소 시한 검증 (canCancel 게이트)**: 상세 조회 plan과 동일한 공용 `canCancelReservation` 함수(도메인 헬퍼) 서버 재검증. 시한 초과 시 `400 CANCELLATION_DEADLINE_EXCEEDED`.
6. **트랜잭션**:
   - `Reservation.status = CANCELED`, `canceledBy = currentUserId`, `cancelReason = null`, `canceledAt = new Date()`
   - `StoreTimeSlot.reservedCount` decrement `participantCount`만큼 (floor 0 보장, decrementReservedCount 패턴 준용)
   - Artwork 존재 시 `Artwork.status = CANCELED`
   - Artwork 존재 시 ArtworkLog 1건 생성: `{ artworkId, changedBy: currentUserId, fromStatus: 기존 Artwork.status, toStatus: CANCELED, memo: null }`
   - (QrToken 처리 없음)
7. 취소 완료 응답 반환.
8. (비동기) 파트너에게 취소 알림 발송 (BullMQ 큐 등록).

### canCancel 게이트 규칙 (상세 조회 plan에서 파생 — 동일 적용)

> SSOT: `docs/exec-plans/active/유저 예약 - 예약 상세조회.md` § canCancel 계산 규칙. 서버 취소 게이트는 이 로직과 **반드시 동일**해야 한다. 현재 구현체: `apps/api/src/modules/reservation/application/use-cases/get-reservation-detail.use-case.ts` `calcCanCancel` 메서드.

```
function calcCanCancel(reservation, store, nowKST):
  if reservation.status not in [PENDING, CONFIRMED]:  return false  // 상태 검증에서 먼저 차단
  if reservation.source != CUSTOMER:                  return false  // userId 검증에서 먼저 차단

  scheduledDateKST = toKSTDate(reservation.scheduledAt)  // KST_OFFSET_MINUTES = 9*60
  todayKST         = toKSTDate(nowKST)

  if todayKST >= scheduledDateKST:                    return false  // 당일 불가 baseline
  effectiveN = max(store.cancelDeadlineDays ?? 1, 1)
  deadlineKST = scheduledDateKST - effectiveN days
  return todayKST <= deadlineKST
```

**공용 추출 (plan 항목 3 참조 — 필수):** `calcCanCancel` 로직이 상세 조회 use-case와 취소 use-case에 중복된다. `apps/api/src/modules/reservation/domain/cancellation-policy.ts`에 `canCancelReservation(status, source, scheduledAt, cancelDeadlineDays, now)` 함수로 추출하고, `toKSTDateNum` / `subDaysNum` 헬퍼는 `date.util.ts`로 승격한다. 상세 use-case의 private `calcCanCancel`을 이 공용 함수 호출로 교체하여 두 use-case가 동일 함수를 공유한다. 이 추출은 #228 리뷰 권고와 연결되며 drift 방지 필수 이행 항목이다.

### 트랜잭션 단계 (구체적 DB 오퍼레이션)

```
BEGIN TRANSACTION
  1. reservation.update({
       where: { id: reservationId },
       data: {
         status: 'CANCELED',
         canceledBy: currentUserId,
         cancelReason: null,          // 바디 없음 — 항상 null
         canceledAt: new Date(),
       }
     })
  2. storeTimeSlot.update({
       where: { id: reservation.storeTimeSlotId },
       data: { reservedCount: Math.max(0, current - reservation.participantCount) }
     })
     // 동시성: decrementReservedCount 패턴 준용
     // (prisma-partner-reservation.repository.ts L404~418 참조)
  3. if (artwork) artwork.update({ where: { id: artwork.id }, data: { status: 'CANCELED' } })
  4. if (artwork) artworkLog.create({
       data: {
         artworkId: artwork.id,
         changedBy: currentUserId,
         fromStatus: artwork.status,   // 트랜잭션 내 조회 시점 status
         toStatus: 'CANCELED',
         memo: null,
       }
     })
  // QrToken 처리 없음 — Artwork.status=CANCELED가 무효 신호
COMMIT
```

   ```
   5. canCancelReservation (공용 도메인 헬퍼 — cancellation-policy.ts) → false이면 400 CANCELLATION_DEADLINE_EXCEEDED
   6. cancelReservation(row, userId) 호출 (트랜잭션, cancelReason 파라미터 없음)
   7. 알림 큐 등록 (비동기, notification 도메인 — MVP이면 stub/skip 가능)
   8. 응답 DTO 조립 반환
   ```

## Risks

- **QrToken 잔존**: Artwork.status=CANCELED 후 QrToken이 DB에 남음. QR 스캔 시 Artwork.status 게이트로 처리. 파트너 QR 스캔 검증 코드에서 실제로 그렇게 동작하는지 구현 착수 전 확인 권고.
- **ArtworkLog fromStatus 경합**: 트랜잭션 내에서 artwork.status를 조회한 뒤 CANCELED로 업데이트해야 fromStatus를 정확히 기록할 수 있음. Prisma `$transaction` 내 `artwork.findUnique` → `artwork.update` → `artworkLog.create` 순서 유지.
- **canCancelReservation 중복 제거 필수**: plan §3 이행 전까지 상세/취소 두 use-case의 규칙 drift 위험. 취소 use-case 작성 시 공용 추출을 함께 진행해야 함.
- **동시성**: 취소와 동시에 다른 예약이 같은 slot에 들어오는 케이스. decrementReservedCount는 `Math.max(0, current - amount)` 패턴으로 underflow만 방지. Prisma 트랜잭션 내에서 처리되므로 격리 수준 기본값(read committed)에서 안전.
