# Feature Plan: 이메일 회원가입

## Summary

- Goal: 이메일/비밀번호 기반 회원가입 플로우(인증코드 발송 → 인증 확인 → 가입 → 자동 로그인) 완성. **BE `auth` 모듈은 PR #42(feat/auth)로 머지·구현됨** — 단 정본 contract와 다수 drift(약관 동의/user_consents 누락, FE 연동 시 400 등, 아래 "BE 구현 현황" 참고). FE 화면은 머지됨(send/verify stub). 남은 작업은 **drift 해소(약관·순서·상태코드 합의) + BE 보정 + FE 실연동**.
- Owner: (미정 — 회원가입 담당자 지정 필요. BE는 feat/auth 작성자와 협의)
- Date: 2026-06-01 (갱신: PR #42 BE 구현 반영 + drift 진단)

## BE 구현 현황 (PR #42 `feat/auth` 머지 — 2026-06-01)

구현 위치: `apps/api/src/modules/auth/` (presentation/controllers·dto, application/use-cases, infrastructure/email), `apps/api/src/redis/`. 전역 `ValidationPipe({ whitelist:true, forbidNonWhitelisted:true, transform:true })`(main.ts L21), 응답 봉투 인터셉터 + all-exceptions 필터 존재.

**구현된 흐름(실제):** send-code → verify-code(Redis `email:verify:{email}` 코드 저장/검증 후 `email:verified:{email}` 플래그 10분) → signup(플래그 확인 후 user 생성, `emailVerified=true`). 즉 **인증을 먼저 하고 가입**하는 순서 = 기능명세 동작 순서를 따름.

### ✅ contract와 일치/해소된 항목
- 인증코드 저장소 = **Redis 확정·구현**(Open decision 2 해소). `email:verify:` TTL 300s(5분), 6자리 숫자.
- 비밀번호 **bcrypt 해싱**(10 rounds). 이메일 중복 = **409 ConflictException**. nickname 미입력 시 **랜덤 생성**(`사용자_XXXXXX`, signup.use-case L9~11).
- signup 응답 shape `{ user: { userId, email, nickname } }` 일치.

### ⚠️🔴 contract ↔ 구현 Drift (해소 필요)

| # | 항목 | 정본 contract | 구현(PR #42) | 심각도 |
|---|------|---------------|--------------|--------|
| D1 | signup 약관 필드 | `termsAgreed`/`privacyAgreed` 필수 | `SignupDto`에 **없음** | 🔴 |
| D2 | `user_consents` 동의 이력 | signup ⑨에서 생성 | **전혀 생성 안 함** | 🔴 |
| D3 | FE↔BE 연동 | FE가 `termsAgreed/privacyAgreed` 전송 | `forbidNonWhitelisted:true` → **추가 필드 400 거부** | 🔴 연동 시 즉시 깨짐 |
| D4 | 인증/가입 순서 | API명세 signup: 가입(`emailVerified=false`) → 이후 인증 | 구현: **인증 먼저**(Redis 플래그) → signup이 `emailVerified=true`로 생성 | ⚠️ API명세 vs 기능명세 자체 충돌, 구현은 기능명세 채택 |
| D5 | 비밀번호 정책 | 영문+숫자+특수문자, **8~32자** | `MinLength(8)`/`MaxLength(100)`만, **복잡도 regex 없음** | ⚠️ |

| D8 | send-code 응답 | `data {email}` | `void`(200) | 경미 |

**최우선(🔴):** D1~D3는 한 덩어리다. 정본은 약관 동의를 받아 `user_consents`에 기록하라는데, 구현은 약관을 아예 안 받고 + `forbidNonWhitelisted`라 FE가 보내면 400. → **반드시 합의 후 한쪽으로 정렬**: (A) BE가 `SignupDto`에 terms/privacy 추가 + `user_consents` 트랜잭션 구현(정본 준수), (B) 약관을 별도 단계/엔드포인트로 분리. 미합의 시 FE 연동 불가.

### 공통 응답 봉투

모든 응답은 `{ statusCode, timestamp, path, message, data, error }` 봉투로 래핑.
- 성공: `error: null`, `data`에 페이로드. 실패: `data: null`, `error`에 도메인 코드 문자열.

### 데이터모델 (출처: `apps/api/prisma/schema.prisma`, 2026-06-01 스냅샷)

- **User** (`users`)
  - `id` String @id @default(uuid()) @db.Uuid
  - `nickname` String @db.VarChar(100)  ← **DB 컬럼은 NOT NULL.** signup 바디에서 nickname 미입력 시 **BE가 랜덤 생성**해 채움(아래 엔드포인트 1 참고).
  - `email` String @unique @db.VarChar(255)
  - `password` String? @db.VarChar(255)  ← 이메일 가입 시 해시 저장(소셜은 null).
  - `isPartner` Boolean @default(false) @map("is_partner")
  - `emailVerified` Boolean @default(false) @map("email_verified")  ← 가입 시 false, verify-code 성공 시 true.
  - `status` UserStatus @default(ACTIVE)  (enum: ACTIVE | WITHDRAWN)
  - `createdAt` / `updatedAt` / `withdrawnAt?`
  - relations: oauthAccounts, refreshTokens(RefreshToken[]), consents(UserConsent[]), notificationSettings 등
- **RefreshToken** (`refresh_tokens`) — 자동 로그인(토큰 발급) 시 사용 가능
  - `id`, `userId`, `tokenHash` VarChar(255), `expiresAt`, `createdAt`
- **PolicyVersion** (`policy_versions`)
  - `id`, `policyType` PolicyType (enum: PRIVACY_POLICY | TERMS_OF_SERVICE | MARKETING), `version` VarChar(20), `url` VarChar(500), `isLatest` Boolean @default(false), `effectiveAt`, `createdAt`
- **UserConsent** (`user_consents`)
  - `id`, `userId`, `policyVersionId`, `isAgreed` Boolean, `agreedAt` @default(now())
  - `@@unique([userId, policyVersionId])`
- 참고: **인증코드 임시 저장용 테이블/저장소는 schema.prisma에 없음.** Redis 또는 신규 임시 테이블 결정 대기(Open decision 2). 테이블 택1 시 prisma 마이그레이션 추가 필요.

### 엔드포인트 1) `POST /auth/signup` — 이메일 회원가입

- 인증: 불필요(Guest). Content-Type: application/json.
- req body (정본):
  ```json
  {
    "email": "user@example.com",
    "password": "Password1234!",
    "nickname": "토담이",
    "termsAgreed": true,
    "privacyAgreed": true
  }
  ```
  - `nickname`: **optional** — 미입력 시 서버가 랜덤 생성해 `users.nickname`에 저장.
  - `passwordConfirm`: **없음**(정본). (미러 stale 무시.)
- 시스템 처리(정본 순서): ① 필수값 검증(email, password, termsAgreed, privacyAgreed) → ② 이메일 형식 검증 → ③ 비밀번호 정책(영문·숫자·특수문자, 8~32자) 검증 → ④ 이메일 중복 조회 → ⑤ 중복이면 중단(409) → ⑥ 약관·개인정보 동의(true) 확인 → ⑦ 비밀번호 해싱 → ⑧ `users` 생성(`status='ACTIVE'`, `is_partner=false`, `emailVerified=false`, nickname=입력값 또는 랜덤) → ⑨ `user_consents` 동의 이력 생성(isLatest PolicyVersion 매핑) → ⑩ 응답.
  - 참고: 정본 처리 흐름은 가입 후 "이후 이메일 인증코드 발송 단계로 전이"로 명시. 즉 signup 시점엔 인증 미완료(`emailVerified=false`)이며 자동 로그인 토큰 발급은 인증 완료(verify-code) 이후로 본다(Open decision 6).
- 201 res data:
  ```json
  { "user": { "userId": "<uuid>", "email": "user@example.com", "nickname": "토담이" } }
  ```
  message "회원가입이 완료되었습니다. 이메일 인증을 진행해주세요."
- 에러:
  - `400 INVALID_REQUEST` — 필수값 누락/이메일 형식/비밀번호 정책 위반.
  - `409 EMAIL_ALREADY_EXISTS` — 이미 가입된 이메일.
  - `500 INTERNAL_SERVER_ERROR`.

### 엔드포인트 2) `POST /auth/email/send-code` — 인증코드 발송

- 인증: 불필요(Guest). Content-Type: application/json.
- req body: `{ "email": "user@example.com" }`
- 시스템 처리(정본): ① email 필수값 검증 → ② 이메일 형식 검증 → ③ 보안 서명 포함 6자리 숫자 코드 생성 → ④ 코드 + 만료시각(now+5분)을 Redis 또는 임시 인증 테이블에 저장 → ⑤ 외부 메일 발송(SendGrid 또는 AWS SES) 호출 → ⑥ 성공 시 완료 응답.
- 200 res data: `{ "email": "user@example.com" }` — message "인증 코드가 이메일로 성공적으로 발송되었습니다."
- 에러:
  - `400 INVALID_EMAIL_FORMAT` — "올바르지 않은 이메일 형식입니다."
  - `500 EMAIL_SEND_FAILED` — "메일 발송 중 서버 내부 오류".

### 엔드포인트 3) `POST /auth/email/verify-code` — 인증코드 확인

- 인증: 불필요(Guest). Content-Type: application/json.
- req body: `{ "email": "user@example.com", "code": "123456" }`
- 시스템 처리(정본): ① 필수값(email, code) 검증 → ② 형식 검증 → ③ 저장소(Redis/임시 테이블)에서 해당 이메일 코드 조회 → ④ 코드 일치 검증 → ⑤ 5분 만료 확인 → ⑥ 통과 시 `users.emailVerified = true` → ⑦ 사용된 코드 저장소에서 파기 → ⑧ 응답.
- 200 res data: `{ "email": "user@example.com", "emailVerified": true }` — message "이메일 인증이 성공적으로 완료되었습니다."
- 에러:
  - `400 INVALID_REQUEST` — "인증 코드는 6자리 숫자여야 합니다." (필수값 누락/형식)
  - `400 INVALID_VERIFICATION_CODE` — "인증 코드가 일치하지 않습니다."
  - `410 VERIFICATION_CODE_EXPIRED` — "인증 시간이 만료되었습니다. 인증 코드를 다시 발송해주세요."
  - `500 INTERNAL_SERVER_ERROR`.

### 검증 규칙 (SSOT: `packages/shared/src/contracts/fields.ts`)

- `emailSchema`: `EMAIL_REGEX`, "이메일 형식이 아닙니다."
- `passwordSchema`: `PASSWORD_REGEX`, "영문·숫자·특수문자를 포함해 8~32자로 입력해주세요." (요구사항 8~32자 정책과 일치)
- `verifyCodeSchema`: 길이 `CODE_LENGTH(=6)` + 숫자만.
- signup composite(`{ email, password, nickname?, termsAgreed, privacyAgreed }`) 스키마는 shared에 **없음** → 신설(Open decision 4). `nickname`은 optional, `passwordConfirm`은 정본에 없으므로 **추가하지 말 것**.

## Open decisions (사람 결정 대기 — 추측 금지)

1. **인증 시도 횟수 제한 정책 미정** (기능명세 비고). send-code 재발송 횟수/쿨다운, verify-code 시도 실패 횟수 제한 정책 정의 필요.

7. **외부 메일 프로바이더.** 구현은 **AWS SES 방향**으로 잡았으나(`EmailService` TODO 주석) 아직 **console.log stub** — 실연동(자격증명/env) 필요(Drift D9).
