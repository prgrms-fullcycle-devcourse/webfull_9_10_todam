## 문제 정의 (이 리팩토링을 하는 이유)

현재는 타임슬롯을 **물리적 행(`StoreTimeSlot`)으로 미리 한 달치 생성**한다. 이 사전생성(pre-generation) 모델에서 슬랙 스레드로 드러난 문제가 누적됐다.

1. **운영시간/간격 변경 시 옛 그리드가 남는다 (핵심 버그).**
   - 6/10 14:00에 예약건이 있는 상태에서 예약 간격을 1h→2h로 바꾸면, 6/10이 `13:00 / 15:00`로 재생성되어야 하는데 예약을 보호하느라 `13:00 / 14:00 / 15:00`이 섞여 남는다.
   - 원인: 예약↔슬롯이 시간이 아니라 **슬롯 ID(`Reservation.storeTimeSlotId`)로 매핑**돼 있어, 기존 예약이 붙은 옛 슬롯 행을 지울 수 없다. (`applyGeneratedGrid`가 예약 있는 stale 슬롯을 DELETE 대신 CLOSED 처리 — `prisma-store-time-slot.repository.ts:85-124`)

2. **한 달치만 생성 → 다음 달이 빈다.**
   - 한 달 동안 공방 수정을 안 하면 다음 달 슬롯이 아예 없다. 스케줄러로 주기 재생성하는 방안도 나왔으나, on-demand로 가면 스케줄러 자체가 불필요.

3. **승인 시점 생성 로직이 (실제로) 없다.**
   - 팀 인식: "어드민 승인 시 생성 / 운영시간 변경 시 재생성". **실제 코드: 둘 다 없음.** 타임슬롯은 파트너가 `POST /partner/stores/:storeId/time-slots/generate`를 직접 호출할 때만 생성된다 (`timeslot.controller.ts:85-99`). 공방 생성/수정/승인은 `operatingHours`만 다루고 슬롯을 만들지 않는다.
   - → SQL로 직접 만든 공방에 슬롯이 없던 것도 이 때문. (FE가 수정 저장 후 generate를 따로 호출해 "수정하면 생긴다"고 보였을 가능성)

4. **파트너가 과거/당일 예약을 못 넣는다.**
   - `buildCandidates`가 `now` 이하 슬롯을 잘라내(`time-slot-generation.service.ts:96-99`) 과거/당일 슬롯 행이 없으니 파트너 수기 예약도 불가.

5. **저장공간 낭비.** 대부분 예약이 안 들어오는 슬롯까지 전부 행으로 적재.

### 대안 비교 (스레드에서 검토한 것)

| 방안 | 내용 | 결론 |
|------|------|------|
| (A) 임시방편 | 운영시간 변경 시 기존 예약 슬롯만 CLOSED + 신규 노출 차단 | UX 혼란은 막지만 근본 해결 X. "임시방편 느낌". |
| (B) 스케줄러 | 주기적으로 다음 달 슬롯 사전생성 | 1·2번만 부분 완화, 1번 근본 원인(ID 매핑) 그대로. |
| **(C) on-demand (본 plan)** | 가상 계산 + 예약 시점 materialize | 1~5번 전부 근본 해결. 리팩토링 규모 큼. |

→ **(C)로 결정.** (B) 스케줄러는 (C)를 채택하면 불필요.

## 설계 (목표 아키텍처)

### 핵심 아이디어

> "슬롯은 운영시간 규칙으로 **언제든 계산 가능한 가상 격자**다. DB 행은 **예약이 실제로 발생할 때만** 만든다."

운영시간(`StoreOperatingHour`) + `reservationIntervalMinutes` + break + `now`만 있으면 임의 날짜의 슬롯 격자를 결정론적으로 재계산할 수 있다. 이 규칙 계산은 이미 `TimeSlotGenerationService.buildCandidates()`에 있다 — 이걸 **단일 진실 소스(SSOT)** 로 삼아 조회/예약 양쪽에서 재사용한다.

### 컴포넌트별 변경

#### A. 도메인 — 그리드 규칙 SSOT (`TimeSlotGenerationService`)

- 기존 `buildCandidates(range, operatingHours, interval, now)` 유지·재활용.
- **[P1] `includePast` 옵션 추가.** 현재 `buildCandidates`는 무조건 `startAt <= now` 슬롯을 제거한다(`time-slot-generation.service.ts:96`). 파트너는 과거+당일 슬롯도 선택해야 하므로(Decision 3) `includePast`(또는 cutoff) 파라미터로 분기.
  - 고객 조회: `includePast=false` (과거 제외, 기존 동작).
  - 파트너 조회: `includePast=true` (과거+당일 포함).
- **추가:** 단일 시각 검증 메서드
  - `isValidCandidate({ startAt, endAt, operatingHours, interval, now, allowPast })`: 요청된 (startAt, endAt)이 *현재* 운영시간 규칙에 맞는 슬롯 경계인지 판정. 예약 시점 검증에 사용. `allowPast`로 파트너 과거/당일 예약 허용 분기(고객 false, 파트너 true).
- 이 메서드들로 "조회에 보이는 슬롯"과 "예약 가능한 슬롯"의 규칙이 항상 일치(drift 제거).

#### B. 조회 변경 — `available-slots` (고객) / `list-time-slots` (파트너)

기존: DB의 `OPEN` 슬롯 행을 읽어 반환.
신규: **가상 격자 계산 + 겹침 기반 정원 집계 (overlap aggregation).**

> **[P0] 핵심 정책 (확정).** 운영시간/interval 변경은 **기존 예약을 변경하지 않는다.** 신규 가상 슬롯의 가용성·잔여 정원은 *동일 (startAt,endAt) 행 하나*가 아니라, **그 슬롯 시간 구간 `[S,E)`과 겹치는 모든 활성 예약**을 기준으로 계산한다.
>
> 단순히 `(startAt,endAt)`이 동일한 슬롯끼리만 `reservedCount`를 공유하는 모델은 **쓰지 않는다** (간격 변경 시 정원 분리 → 초과예약 발생).

알고리즘 (가상 슬롯 `[S,E)` 하나 기준):

1. `buildCandidates`로 범위 내 가상 격자 계산.
2. 조회 범위 `[range_start, range_end)`과 **겹치는** 활성 예약을 `(scheduledAt, scheduledEndAt, participantCount)`로 조회. ⚠️ `scheduledEndAt` 신규 컬럼 필요 (아래 J 참조).
   - **[P0] 겹침 조회 조건(Decision 23): 시작 시각이 범위 안인 것만 가져오면 안 된다.** 범위 시작 이전에 시작해 내부로 이어지는 예약을 놓치므로, **구간 겹침** 조건으로 조회:
     ```sql
     scheduled_at   <  :range_end
     AND scheduled_end_at >  :range_start
     AND status != 'CANCELED'
     ```
   - 동일 range-overlap 조건을 **CLOSED/CANCELED 슬롯 행 조회**(`start_at < range_end AND end_at > range_start`)와 **ReservationRestriction 조회**(`start_at < range_end AND end_at > range_start`)에도 적용.
   - **활성 예약 정의(Decision 20): `status != CANCELED`** = `{PENDING, CONFIRMED, IN_PROGRESS, SHIPPED, DELIVERED, PICKUP_READY, PICKUP_DONE}`. 기존 `reservedCount` 시맨틱(생성 시 increment, 취소 시에만 decrement)과 정확히 일치 — 좌석은 취소돼야만 반환된다.
3. `[S,E)`과 겹치는(`resStart < E && S < resEnd`) 활성 예약 집합 `O`를 구한다.
4. **겹침 정원 차감:** 예약이 슬롯 경계를 가로질러도 해당 슬롯과 겹치면 점유 인원을 차감한다. `remainingCount = maxCapacityPerSlot − Σ participantCount(O)`.
6. **[P1] CLOSED/CANCELED 겹침 차단 (확정).** 닫힌 시간대도 *예약과 동일하게 겹침 기반*으로 차단한다 — 정확히 같은 `[S,E)` 행만 보지 않는다. 범위 내 `status∈{CLOSED,CANCELED}` 행들의 `[cStart,cEnd)`를 모아, 신규 슬롯 `[S,E)`과 **겹치면 `isAvailable=false`** (임시휴무 의도가 간격 변경 후에도 유지). 예: `14:00~15:00` CLOSED → 간격 변경 후 `13:00~15:00` 슬롯도 차단.
7. 최종:
   `isAvailable = 현재격자유효 && !겹치는CLOSED/CANCELED && remainingCount>0 && !restricted`.

겹침 판정 예시 (정원 5 기준):

| 기존 활성 예약 | 신규 슬롯 | 결과 |
|---|---|---|
| 14:00~15:00, 2명 | 13:00~15:00 | 잔여 3 (contained → 차감) |
| 14:00~16:00, 2명 | 13:00~15:00 | 잔여 3 (경계 횡단 겹침 → 차감) |
| 14:00~15:00 | 15:00~17:00 | 영향 없음 (미겹침) |

> 옛 규칙으로 만들어진 예약은 격자에서 사라져 신규로 노출되지 않지만, 위 집계로 **그 시간대와 겹치는 신규 슬롯의 정원/가용성에 정확히 반영**된다. → 문제 1(정원 분리) 근본 해결.

> **단순화 포인트(동시성 근거).** 단일 현재 운영규칙 하의 격자는 back-to-back이라 **서로 겹치지 않는다**. 겹침은 *옛 규칙 기존예약 ↔ 새 격자* 에서만 생기고 기존 예약은 불변. → 규칙 변경이 없던 평상시엔 `O`가 비어 정원 = 그 슬롯 자기 예약뿐(기존과 동일).

> **파트너 변경 시 경고(soft).** interval/운영시간 변경 저장 시 영향받는 미래 활성 예약이 있으면 **하드 차단하지 않고** "기존 예약 N건이 새 시간표와 겹쳐 해당 시간대 신규 예약이 제한됩니다" 경고만 노출.

#### C. 예약 생성 변경 — lazy materialization (가장 큰 변경)

기존: FE가 `slotId`(DB 행 id) 전달 → 행 조회 → `tryIncrementReservedCount`.
신규: FE가 **시각(startAt) 전달** → 검증 → materialize → 증가.

트랜잭션 내:

0. **[P0] 공방 단위 lock 획득.** 겹침 집계(3)와 정원 증가(5) 사이, 그리고 다른 쓰기와의 경합을 막기 위해 **트랜잭션 시작 직후 공방 단위 직렬화 lock**을 잡는다.
   - **방식 확정(Decision 17): `SELECT id FROM stores WHERE id = :storeId FOR UPDATE`.** (advisory lock 대비 단순·명시적, 트랜잭션 종료 시 자동 해제.)
   - **동일 lock 적용 대상(설계 K, Decision 18) — 슬롯 가용성을 바꾸는 모든 쓰기:**
     1. 예약 생성(고객·파트너 수기)
     2. 운영시간/interval 변경(`PrismaUpdateStoreCommand`)
     3. 슬롯 상태변경(OPEN/CLOSED/CANCELED, 설계 D)
     4. ReservationRestriction 생성/해제
   - 이유: 예약이 CLOSED/restriction/겹침을 검사한 직후 동시에 차단 설정이 생성되면 예약이 통과할 수 있다(TOCTOU). 위 쓰기를 공방 단위로 직렬화해 `O_other`·격자·차단 상태가 트랜잭션 동안 **불변임을 lock으로 실제 보장**한다.
1. store PUBLISHED / program ACTIVE 검증 (기존 유지).
2. **`isValidCandidate`로 현재 운영시간 대비 유효성 검증** (고객 `allowPast=false`, 파트너 `allowPast=true`). 무효면 `INVALID_SLOT(400)`.
3. **[P0] 겹침 집계 (조회 B와 동일 규칙, range-overlap 조건).** 요청 `[S,E)`과 겹치는:
   - **CLOSED/CANCELED 행과 겹치면** → `SLOT_BLOCKED(409)` (B-6).
   - **(해당 프로그램의) ReservationRestriction 구간과 겹치면** → `SLOT_BLOCKED(409)` (설계 G).
   - 활성 예약 중 **이 슬롯 자체 예약을 제외한**(= 옛 규칙 기존예약) 집합 `O_other` 계산. 경계를 가로지르는 예약도 점유 인원에 포함한다.
   - `otherOverlap = Σ participantCount(O_other)`.
4. **슬롯 materialize** = `createMany([{storeId,startAt,endAt,status:OPEN,reservedCount:0}], { skipDuplicates: true })` → 이미 있으면 무시. 직후 행 조회로 `id` 확보. (Decision 5)
5. **유효정원으로 원자 증가.** 기존 `tryIncrementReservedCount`를 재사용하되 cap을 낮춘다:
   `effectiveCap = maxCapacityPerSlot − otherOverlap`.
   `updateMany(where: { id, status:OPEN, reservedCount ≤ effectiveCap − participantCount }, data: { reservedCount: increment })`. 영향 0건 → `INSUFFICIENT_CAPACITY`.
   - 근거: 0번 lock으로 `O_other`가 트랜잭션 동안 **불변 보장**. 같은 슬롯 동시 신규 예약은 이 슬롯 행의 `reservedCount` 원자 CAS가 직렬화. 임의 시점 합계 ≤ `reservedCount(this) + otherOverlap ≤ effectiveCap + otherOverlap = maxCapacity`. → 초과예약 불가.
   - 평상시(규칙 변경 없음)엔 `otherOverlap=0` → 기존 로직과 동일.
6. 이하 동일(snapshot, reservation 생성 — `scheduledEndAt`도 함께 기록, autoConfirm 시 Artwork/QR).

> `Reservation.storeTimeSlotId` FK는 유지된다. 슬롯을 "예약 직전에 만들어서" 그 id를 붙이는 것뿐. `reservedCount`는 *이 슬롯 자체* 예약 누적용으로 계속 쓰이고, 겹치는 옛 예약은 `effectiveCap`으로 흡수.

> **[P0] 파트너 수기예약도 동일 경로 (Decision 19).** `createManual`은 위 0~6(공방 lock·현재격자 검증·CLOSED/restriction 검사·겹침 집계·`effectiveCap` 증가·`scheduledEndAt` 기록)을 **고객 예약과 동일하게** 거친다. 차이는 `allowPast=true`(과거/당일 허용)와 `source=PARTNER_MANUAL`·`userId=null`뿐. → 검증·동시성 로직을 **공유 booking core**로 추출해 두 repository가 같이 쓰도록 한다(드리프트 방지).

> **[P0] 배포 호환 (Decision 6·10) — slotId 경로도 신규 검증으로 정규화.** `POST /reservations`는 전환기 `slotId | startAt` 둘 다 받지만, **두 경로 모두 동일한 현재 격자 검증·겹침 집계를 거친다.** `slotId`가 오면 → 그 행의 `startAt`/`endAt`을 읽어 `startAt`으로 정규화한 뒤 위 1~6을 그대로 수행. **기존 행을 그냥 increment하는 우회 경로는 두지 않는다.** 따라서 간격 변경 후 구버전 FE가 **stale slot**(현재 격자에 없는 옛 슬롯)에 예약하면 `isValidCandidate` 실패 → `INVALID_SLOT(400)`. 현재 격자에 여전히 유효한 슬롯이면 정상 예약. (BE dual-accept 배포 → FE startAt 전환 배포 → BE slotId 제거 순.)

#### D. 파트너 슬롯 닫기/취소/재오픈 — [P0] `slotKey` 기반 계약

- 가상 모델에선 "닫을 행"이 없다 → **닫기 = CLOSED 행을 materialize**.
- 현재 `PATCH .../time-slots/:timeSlotId/status`는 **UUID만** 받아 가상 슬롯을 닫을 수 없다 (`timeslot.controller.ts:118`).
- **[P0] 계약 변경 — `slotKey`(= `startAt|endAt`) 입력.** `startAt`만 받으면 안 되는 이유: `14:00~15:00`을 CLOSED한 뒤 interval이 2h로 바뀌면, 재오픈 요청 `startAt=14:00`이 현재 interval로 `14:00~16:00`을 계산해 **기존 CLOSED 행 `14:00~15:00`을 못 짚는다 → 차단 영구 해제 불가**(P0 버그). `slotKey`로 정확한 `(startAt,endAt)` 행을 지목.
  ```
  PATCH /partner/stores/{storeId}/time-slots/status
  { "slotKey": "2026-06-10T05:00:00.000Z|2026-06-10T06:00:00.000Z", "status": "CLOSED" }
  ```
- 동작(공방 lock 하에):
  - **CLOSE/CANCEL**: `slotKey`가 **현재 격자에 유효한** 슬롯일 때만 허용(`isValidCandidate`) → `(storeId,startAt,endAt)` `createMany(skipDuplicates)`로 materialize 후 status 전이.
  - **OPEN(재오픈)**: 현재 격자 유효성 **검사하지 않는다.** stale CLOSED/CANCELED 행(간격 변경으로 격자에서 사라진)도 지목해 OPEN으로 되돌려 **차단을 해제**할 수 있어야 하므로. 행이 있으면 status→OPEN(예약 0건이면 삭제도 가능), 없으면 no-op.
- `UpdateTimeSlotStatusUseCase`를 `slotKey` 입력 기반으로 재작성.

#### E. 기존 사전생성 코드 처리

- `GenerateTimeSlotsUseCase` / `applyGeneratedGrid` / `POST .../time-slots/generate` 엔드포인트 → **제거** (Decision 4, 단 맨 마지막 단계).
- 스케줄러 도입 **불필요**.

#### K. [P0] 공방 lock 적용 대상 — 슬롯 가용성 변경 쓰기 전부 직렬화

슬롯 가용성·정원·차단 상태에 영향을 주는 **모든 쓰기**가 동일한 공방 row lock(`SELECT id FROM stores WHERE id=:storeId FOR UPDATE`, Decision 17)을 트랜잭션 시작 직후 획득한다:

| 쓰기 | 파일 | lock 이유 |
|------|------|----------|
| 예약 생성(고객·수기) | `prisma-user-reservation`·`prisma-partner-reservation` | 겹침 집계↔정원 증가, 격자/차단 검사↔쓰기 직렬화 |
| 예약 취소/거절(정원 decrement) | `cancel-user-reservation`·파트너 거절 경로 | 정원 증가와 일관된 계산 — 동시 생성↔취소 경합 직렬화 |
| 운영시간/interval 변경 | `prisma-update-store.command.ts:88-104` | 예약 도중 규칙 변경 시 격자·`O_other` 흔들림 차단 |
| `maxCapacityPerSlot` 변경 | `prisma-update-store.command.ts` (예약정보 저장) | 정원 검사↔정원 변경 경합 차단 |
| 슬롯 상태변경 | `update-time-slot-status.use-case.ts` | 예약 검사 직후 CLOSE 생성되는 TOCTOU 차단 |
| ReservationRestriction 생성/해제 | restriction use-case | 예약 검사 직후 restriction 생성되는 TOCTOU 차단 |

→ 검사(CLOSED/restriction/overlap)와 그 결정에 영향 주는 상태 변경이 절대 끼어들 수 없어, `O_other`·격자·차단 상태의 트랜잭션 내 불변을 **lock으로 실제 보장**. 변경 작업은 기존 예약을 손대지 않으므로(설계 B) lock 범위는 짧다.

> **[P0] lock과 쓰기는 반드시 동일 트랜잭션 내.** `FOR UPDATE`는 트랜잭션 종료 시 해제되므로, 위 모든 쓰기는 **`$transaction` 블록 첫 구문에서 `SELECT … FOR UPDATE`를 실행하고 같은 트랜잭션 안에서** 검사·materialize·정원증가·상태변경/restriction 쓰기를 완료해야 효력이 있다. lock과 쓰기가 다른 트랜잭션이면 직렬화가 깨진다.

#### F. [P0] 가상 슬롯 식별자 `slotKey` — 파트너 전 계약 시각 기반 전환

가상 슬롯은 UUID가 없으므로, 파트너 응답/요청이 `slotId(UUID)`에 의존하던 곳을 **`slotKey`로 전환**한다.

> **[P1] `slotKey` 정의 확정: `slotKey = ISO(startAt)|ISO(endAt)`.** 스키마 유니크가 `(storeId, startAt, endAt)`이라 **같은 startAt에 다른 endAt 공존이 허용**된다(간격 변경 후 격자가 섞일 때). startAt 단일값으론 모호 → `startAt|endAt` 조합으로 고정. 서버는 `slotKey`를 파싱해 `(startAt,endAt)`로 복원, 항상 현재 격자 유효성 재검증.

영향 계약 (모두 시각 기반 전환):

| 대상 | 현재 | 전환 |
|------|------|------|
| `TimeSlotItem.slotId` (`packages/shared/.../timeslot.ts:160`) | UUID | `slotKey`(startAt/endAt)로 대체 |
| `TimeSlotItem.createdAt` (`:169`) | DB 행 생성시각 | 가상 슬롯엔 무의미 → 제거 또는 `null` 허용 |
| 슬롯 상태변경 API | `:timeSlotId` path | 위 D의 `{slotKey,status}` body |
| 프로그램 예약건수 `timeSlotIds` (`:185`) | 콤마구분 UUID | 콤마구분 `slotKey` 목록(또는 date만으로 전체) |
| 파트너 수기예약 슬롯 선택 (`PartnerReservationManualCreateClient.tsx:125`) | slotId 선택상태 | `slotKey` 선택상태 |
| 예약 제한(restriction) UI 슬롯 선택 | slotId | `slotKey` |

#### G. [P0] ReservationRestriction — 겹침 기반 차단

- **현 검사는 정확 일치**(`(storeId, startAt, programId)` unique, `:185` 부근)라 CLOSED와 같은 우회가 발생한다: `14:00~15:00` 제한 후 격자가 `13:00~15:00`으로 바뀌면 **제한이 적용 안 됨**.
- `ReservationRestriction`은 이미 `startAt`/`endAt`을 둘 다 보유(`schema.prisma:303-304`) → **스키마 변경 없이 겹침 기반 차단 가능.**
- **정책 확정(Decision 22): CLOSED와 동일하게 겹침 기반.** 신규 가상 슬롯 `[S,E)`이 (해당 프로그램의) restriction 구간 `[rStart,rEnd)`과 겹치면 그 슬롯·프로그램은 `restricted=true` → 예약 시 `SLOT_BLOCKED(409)`. 정확 일치가 아니라 시간구간 겹침으로 판정. (초기화 방식 미채택 — CLOSED 결정과 일관.)

#### J. [P0] 스키마 추가 — `Reservation.scheduledEndAt`

겹침 정원 집계(B·C)는 활성 예약마다 **종료 시각**이 필요하다. 현재 `Reservation`엔 `scheduledAt`(= slot.startAt)만 있고 종료 시각이 없다 (`schema.prisma:316-352`).

- 슬롯 FK로 `StoreTimeSlot.endAt`을 조인해 얻을 수도 있으나, **마이그레이션으로 OPEN 빈 슬롯을 삭제**하고(Decision 2) 슬롯 의존을 줄이는 방향이므로, 예약에 **종료 시각 스냅샷**을 갖는 것이 장기적으로 안전·단순.
- **추가:** `Reservation.scheduledEndAt DateTime @db.Timestamptz(6)`.
  - 신규 예약: 생성 시 `slot.endAt`으로 기록.
  - 백필: 기존 예약은 `storeTimeSlot.endAt`(없으면 `scheduledAt + interval`)로 채움.
- 겹침 조회는 슬롯 조인 없이 `reservations(scheduledAt, scheduledEndAt, participantCount, status)`만으로 수행 → 쿼리 단순.

> ⚠️ 이 추가로 본 plan은 **스키마 변경을 1건 동반**한다(아래 영향 범위 갱신).

#### H. [P1] 조회 범위 필수 + 상한

- 가상 격자는 범위가 없으면 무한 계산 → **범위 파라미터 필수화**.
- `available-slots`: `year`+`month` 필수(현행 유지).
- `list-time-slots`(파트너): 현재 `date`/`startDate`/`endDate`가 전부 optional(`timeslot.ts:140-149`)이라 무범위 호출 가능 → **`date` 또는 `startDate`+`endDate` 중 하나 필수**로 변경하고, 범위 **최대 길이 상한(예: 92일 = 약 3개월)** 적용. 초과 시 `RANGE_TOO_WIDE(400)`.

## Decisions (확정 — 2026-06-14)

1. **[확정] slotId 계약 = (a) startAt 전달.** `POST /reservations` Body에서 `slotId` 제거, `startAt` 전달(서버가 store `reservationIntervalMinutes`로 `endAt` 도출). `available-slots` 응답 식별 필드도 `startAt` 기반으로 변경. **FE 변경 동반.**

2. **[확정] 기존 행 마이그레이션 = (a) 삭제.** 예약 0건 `OPEN` 행 삭제(저장공간 회수), 예약 있는 행·CLOSED/CANCELED 보존. 단 **즉시 실행하지 않고 코드 전환이 모두 끝난 뒤** 마이그레이션 스크립트로 정리(단계 6 이후).

3. **[확정] 파트너 과거/당일 예약 모두 허용.** 파트너 수기 예약은 `allowPast=true` — 과거 + 당일 시각 모두 예약 생성 가능. (고객은 `allowPast=false` 유지.)

4. **[확정] `generate` 엔드포인트 = 제거. 단 맨 마지막 작업.** 조회/예약/파트너 전환이 다 검증된 뒤 제거(단계 6). 전환기 중에는 남겨두어 안전망으로 사용.

5. **[확정] 동시성 = `createMany(skipDuplicates)`.** 예약 시 `createMany([slot], skipDuplicates: true)`로 슬롯 행을 만들고(이미 있으면 무시) → 조회 → 기존 원자 CAS(`tryIncrementReservedCount`)로 증가. P2002 재시도 불필요.

### 검토 반영 추가 확정 (2026-06-14, 2차 리뷰)

6. **[확정/P0] 겹침 정원 정책 = overlap aggregation.** (설계 B·C) 운영시간·interval 변경은 기존 예약을 바꾸지 않는다. 신규 가상 슬롯 `[S,E)`의 가용성·잔여는 **그 구간과 겹치는 모든 활성 예약**을 기준으로 계산한다. 슬롯 경계를 가로지르는 예약도 `remaining = maxCap − Σ participantCount`로 차감한다. `(startAt,endAt)` 동일 슬롯끼리만 reservedCount를 공유하는 모델은 **미채택**. 동시성은 `effectiveCap = maxCap − otherOverlap`으로 기존 원자 CAS 재사용. → **`Reservation.scheduledEndAt` 컬럼 추가 동반(설계 J).**

7. **[대체됨 → Decision 21]** ~~파트너 슬롯 상태변경 = `{startAt,status}` 시각 기반 계약.~~ `slotKey`(startAt|endAt) 입력으로 확정됨(재오픈 시 stale 행 지목 필요). 본 항목은 **Decision 21로 대체**.

8. **[확정/P0] 가상 식별자 `slotKey` 도입.** (설계 F) `slotId(UUID)`에 의존하던 파트너 전 계약(목록 응답·수기예약·제한 UI·예약건수 집계)을 `slotKey`(startAt/endAt 기반)로 전환. `TimeSlotItem.createdAt`은 제거/null 허용.

9. **[확정/P1] 파트너 과거 조회 = `buildCandidates(includePast=true)`.** (설계 A) 고객은 `includePast=false`. 단순 `isValidCandidate(allowPast)`만으로는 *목록*에 과거 슬롯이 안 떠 선택 불가 → 조회 빌더에도 분기 필요.

10. **[확정/P1] 예약 계약 배포 호환.** (설계 C) `POST /reservations`는 전환기 `slotId | startAt` dual-accept. **BE dual-accept 배포 → FE startAt 전환 배포 → BE slotId 제거** 순. 예약 실패 윈도우 없음.

11. **[확정/P1] 파트너 list 범위 필수+상한.** (설계 H) `date` 또는 `startDate`+`endDate` 필수, 최대 92일.

12. **[확정/P2] 마이그레이션 삭제 조건 정밀화.** "예약 0건 OPEN 행" = `status=OPEN AND NOT EXISTS (SELECT 1 FROM reservations r WHERE r.store_time_slot_id = s.id)` — **모든 상태(취소 포함)의 Reservation**을 참조 검사해 FK 오류 회피. CLOSED/CANCELED 행도 보존.

### 검토 반영 추가 확정 (2026-06-14, 3차 리뷰)

13. **[확정/P0] 공방 단위 lock으로 쓰기 직렬화.** (설계 C-0·K) 슬롯 가용성에 영향 주는 쓰기가 동일 공방 lock(방식은 Decision 17, 대상은 Decision 18)을 잡는다. `O_other` 불변 가정을 가정이 아니라 lock으로 **실제 보장**.

14. **[확정/P0] dual-accept `slotId` 경로도 신규 검증으로 정규화.** (설계 C) `slotId` 입력 시 그 행의 `startAt`/`endAt`을 읽어 startAt 경로로 정규화 후 **동일한 현재 격자 검증·겹침 집계**를 거친다. 기존 행 단순 increment 우회 없음. → 간격 변경 후 구버전 FE의 **stale slot 예약은 `INVALID_SLOT`**, 현재도 유효한 슬롯은 정상.

15. **[확정/P1] `slotKey = startAt|endAt`.** (설계 F) 같은 startAt에 다른 endAt 공존(유니크가 `(storeId,startAt,endAt)`)을 식별하기 위해 startAt 단일값이 아닌 `startAt|endAt` 조합으로 확정.

16. **[확정/P1] CLOSED/CANCELED = 겹침 기반 차단 유지.** (설계 B-6·C-3) 닫힌 시간대도 예약과 동일하게 시간구간 겹침으로 차단. 간격 변경으로 격자가 달라져도 임시휴무 의도 유지. (초기화 방식 미채택.)

### 검토 반영 추가 확정 (2026-06-14, 4차 리뷰)

17. **[확정/P1] lock 방식 = `SELECT … FROM stores WHERE id = :storeId FOR UPDATE`.** (설계 C-0) advisory lock 대신 Store row lock으로 단일 확정.

18. **[확정/P0] lock 적용 대상 = 슬롯 가용성·정원 변경 쓰기 전부.** (설계 K) 예약 생성(고객·수기) / 예약 취소·거절(정원 decrement) / 운영시간·interval 변경 / `maxCapacityPerSlot` 변경 / 슬롯 상태변경 / ReservationRestriction 생성·해제. TOCTOU(검사 직후 차단 생성) 및 정원 계산 일관성 확보.

19. **[확정/P0] 파트너 수기예약 = 공유 booking core.** (설계 C) `createManual`이 고객 예약과 동일한 lock·격자검증·CLOSED/restriction·overlap·effectiveCap·scheduledEndAt 경로를 사용. 차이는 `allowPast=true`·`source=PARTNER_MANUAL`뿐.

20. **[확정/P1] 정원 차감 대상 = `status != CANCELED`.** (설계 B-2) `{PENDING,CONFIRMED,IN_PROGRESS,SHIPPED,DELIVERED,PICKUP_READY,PICKUP_DONE}`. 기존 reservedCount 시맨틱과 일치.

21. **[확정/P0] 슬롯 상태변경 API = `slotKey`(startAt|endAt) 입력.** (설계 D) OPEN(재오픈)은 stale 행도 지목 가능(격자 검증 면제)해 간격 변경 후에도 CLOSED 차단을 해제할 수 있게 한다. CLOSE/CANCEL은 현재 격자 유효 슬롯만.

### 검토 반영 추가 확정 (2026-06-14, 5차 리뷰)

22. **[확정/P0] ReservationRestriction = 겹침 기반 차단.** (설계 G) 정확 일치가 아닌 시간구간 겹침(`[S,E)` vs `[rStart,rEnd)`)으로 판정. `endAt`이 이미 스키마에 있어 변경 없이 가능. CLOSED 결정과 일관(초기화 미채택).

## API Contract (변경 스냅샷)

> Decisions 1~24 반영본. Notion API명세 갱신 시 이 섹션 diff로 추적.

### `POST /reservations` (변경)

| 필드 | 변경 전 | 전환기(dual) | 최종 |
|------|---------|--------------|------|
| slotId | UUID (필수) | optional (허용) | **제거** |
| startAt | — | optional (허용) | Timestamptz (필수) |
| (그 외) | programId, participantCount, reserverName/Phone, deliveryMethod, requestMemo … | 동일 | 동일 |

> 전환기엔 `slotId | startAt` 중 하나 필수(둘 다 없으면 400). Decision 10 배포 순서 참고.

신규 에러: `INVALID_SLOT(400)`(요청 시각이 현재 격자에 없음), `SLOT_OVERLAP(409)`(슬롯 범위를 벗어나 걸치는 기존 예약 존재 = spill).
기존 에러 유지: `INSUFFICIENT_CAPACITY`(겹침 합계 포함 정원 초과), `SLOT_BLOCKED`, `SELF_RESERVATION_NOT_ALLOWED`.

### `GET /programs/{programId}/available-slots` (응답 의미 변경)

- 쿼리 `year`, `month` 동일.
- 응답 슬롯 배열: DB 행이 아닌 **가상 격자**. 식별 필드 `id`(UUID) → `slotKey`(startAt/endAt) (Decision 1·8).
- 각 슬롯: `startAt`, `endAt`, `remainingCount`(= maxCapacity − reservedCount), `isAvailable`(겹침·정원·restricted·status 반영).

### `GET /partner/stores/{storeId}/time-slots` (응답 의미 변경)

- 가상 격자 + 겹침집계 정원 + `includePast=true`. CLOSED/CANCELED는 **겹침 기반 차단**(설계 B-6).
- **범위 필수**: `date` 또는 `startDate`+`endDate` (최대 92일). 미지정/초과 시 400 (Decision 11).
- `TimeSlotItem`: `slotId`→`slotKey`, `createdAt` 제거/null (Decision 8).
- `TimeSlotItem.blockingSlotKeys`: 현재 가상 슬롯과 겹치는 물리 CLOSED/CANCELED 행의 정확한 `slotKey` 목록. stale 차단 행을 `PATCH .../status {status:OPEN}`으로 해제할 때 사용.

### `PATCH /partner/stores/{storeId}/time-slots/status` (신규 — 기존 `:timeSlotId/status` 대체)

- Body: `{ slotKey: "startAtISO|endAtISO", status: OPEN|CLOSED|CANCELED }`. CLOSE/CANCEL은 현재 격자 유효 슬롯만, OPEN(재오픈)은 stale 행도 허용 (Decision 7·설계 D). 공방 lock 하 실행.

## 단계별 작업 순서 (= 실제 실행 순서)

> 핵심 제약: **계약 제거/엔드포인트 제거는 FE 전환 배포 이후.** 아래 번호 = 실행 순서.

0. **스키마 선행** — `Reservation.scheduledEndAt` 컬럼 추가 마이그레이션 + 기존행 백필(`storeTimeSlot.endAt`) + 신규 예약 경로가 채우도록 기록(설계 J). 겹침 집계의 전제.
1. **도메인 SSOT** — `includePast` 옵션 + `isValidCandidate` + **겹침(overlap/spill) 집계 헬퍼** 추가 + 단위 테스트(운영시간 경계/break/과거/요일휴무/contained·spill 겹침).
2. **조회 전환** — `available-slots`·`list-time-slots` 가상격자+겹침집계 정원+**CLOSED/CANCELED·restriction 겹침 차단**+range-overlap 조회조건+범위필수(상한) 재작성 → 회귀 테스트(간격 변경 후 contained 차감/spill 차단/미겹침 무영향/CLOSED·restriction 유지 = 문제 1).
3. **예약 전환 — 공유 booking core (BE, dual-accept)** — `slotId|startAt` 둘 다 동일 검증 경로로 정규화. **공방 lock(FOR UPDATE)**+격자검증+CLOSED/restriction/겹침집계(`O_other`)+`createMany(skipDuplicates)`+`effectiveCap` 원자증가. 고객·수기 공용 core로 추출. 동시성·stale slotId 경합 테스트. (Decision 10·13·14·17·19·20)
4. **설정변경/제한 lock + 파트너 수기예약** — `PrismaUpdateStoreCommand`·ReservationRestriction 생성/해제에 동일 공방 lock(설계 K); 수기예약은 core 재사용 + `allowPast=true` (문제 4).
5. **슬롯 상태 관리** — `PATCH .../time-slots/status {slotKey}` 재작성: CLOSE/CANCEL은 현재격자 유효 슬롯만, OPEN(재오픈)은 stale 행도 허용해 차단 해제 가능. 공방 lock 하 실행. (Decision 21)
6. **계약/FE 전환** — `slotKey` 적용(목록·수기예약·제한 UI·예약건수), 예약 요청 startAt 전환, `StudioEditLayout` generate 호출 제거, closed 슬롯 노출 차단. **배포.** (Decision 10 ②)
7. **레거시 제거 (마지막)** — FE 전환 배포 확인 후: `POST /reservations`에서 `slotId` 제거(Decision 10 ③), `generate` 엔드포인트/`GenerateTimeSlotsUseCase`/`applyGeneratedGrid` 제거, `generateTimeSlots` FE API 제거.
8. **마이그레이션 (최후)** — `OPEN AND NOT EXISTS(모든 상태 Reservation)` 행 삭제 스크립트 실행.

> 순서 주의: **7·8(제거/정리)은 반드시 6(FE 전환 배포) 이후.** FE가 generate를 안 부르고 startAt으로 예약하도록 먼저 배포돼야 BE에서 엔드포인트·slotId를 지워도 404/400이 안 난다.
