# 푸시 알림 정책 및 유즈케이스

> 대상 채널: **Web Push (FCM)** — PWA / 브라우저 푸시 단일 채널 (MVP)
> 도메인: `notification` — 상태 변경 트리거에 따른 자동 알림 관리
> 연결 도메인: `reservation`, `artwork`, `store`, `partner`, `review`

---

## 1. 목적

도자기 체험은 예약·결제 이후 평균 30일의 제작 리드타임 동안 정보가 단절된다. 푸시 알림은 이 공백 구간의 상태 변화를 **고객·파트너 양측에 적시 전달**하여, 고객의 대기 경험을 콘텐츠로 전환하고 파트너의 운영 누락을 방지하는 것을 목표로 한다.

알림은 **상태 변경의 부수 효과(side effect)** 로만 발생하며, 알림 발송 실패가 원 트랜잭션(예약 확정, 작품 단계 전이 등)을 롤백시키지 않는다.

## 2. 기본 원칙

| 원칙 | 내용 |
|------|------|
| **이벤트 기반** | 도메인 상태 전이 시점에만 큐에 적재. 폴링·스케줄 알림은 정체 보정(estimatedCompletedAt) 등 명시된 경우만 허용 |
| **수신자 분리** | 한 이벤트가 고객/파트너 양측 대상일 수 있으며, 각각 별도 메시지·딥링크로 발송 |
| **멱등성** | `(eventType, targetId, recipientId)` 기준 중복 발송 차단. 재시도 시에도 1회만 도달 |
| **비동기·비차단** | 알림 큐 등록은 원 트랜잭션 커밋 이후. 발송 실패는 원 상태에 영향 없음 |
| **권한 일치** | 딥링크 진입 시점에 수신자의 자원 접근 권한 재검증 (알림 발송 후 권한 변동 가능) |
| **수신 동의** | 브라우저 푸시 권한(Notification.permission) 미허용 시 발송 생략, 인앱 알림센터로 폴백 |
| **조용한 시간** | 야간(22:00~08:00) 비긴급 알림은 익일 오전으로 지연 발송 (긴급: 취소·반려 제외) |

## 3. 알림 카테고리

| 카테고리 | 수신자 | 옵트아웃 | 긴급도 |
|----------|--------|----------|--------|
| **거래 필수** (예약 확정·취소·반려) | 고객 / 파트너 | 불가 | 긴급 |
| **제작 진행** (작품 단계 전이) | 고객 | 가능 | 일반 |
| **수령** (발송·픽업 준비·수령 완료) | 고객 | 불가 | 긴급 |
| **운영** (공방 검수·파트너 상태) | 파트너 | 불가 | 긴급 |
| **참여 유도** (리뷰 요청·재방문) | 고객 | 가능 | 낮음 |

> 거래 필수·수령·운영 카테고리는 서비스 신뢰와 직결되므로 옵트아웃 불가.

## 6. 발송 파이프라인

```
도메인 상태 전이 (트랜잭션 커밋)
  → notification 큐 등록 (eventType, targetId, recipientId, payload)
  → 멱등성 키 검사 (중복 차단)
  → 수신 동의/조용한시간/옵트아웃 정책 적용
  → FCM 발송 (web push)
  → 결과 기록 (성공/실패/재시도)
  → 인앱 알림센터 동기 적재 (푸시 미수신 폴백)
```

- **재시도**: FCM 일시 오류 시 지수 백오프 최대 3회. 영구 실패(토큰 무효)는 토큰 폐기.
- **토큰 관리**: 디바이스별 FCM 토큰 등록/갱신/만료 처리. 로그아웃 시 토큰 해제.
- **폴백**: 푸시 권한 미허용·발송 실패 시에도 인앱 알림센터에는 항상 적재.

## 8. MVP 범위 정리

**포함**: 거래 필수(U-1~U-3, P-1~P-2), 수령(U-11~U-14), 운영(P-6~P-9), 작품 진행(U-5~U-9), 인앱 알림센터, 옵트아웃 설정.

**제외(차기)**: 카카오 알림톡·이메일 다채널, 배송 실시간 추적 연동, 스케줄 리마인더(U-4·P-3) 정교화, 마케팅/재방문 캠페인.

## 9. 구현 순서 (iOS 포함)

> iOS Safari web push는 **홈화면 설치된 PWA에서만** 동작(iOS 16.4+). 따라서 manifest·설치 플로우가 1단계 필수.

### 1단계 — PWA 기반
- `manifest.webmanifest`: `name`, `icons`(192·512), `display: standalone`, `start_url`
- service worker 등록 (`public/firebase-messaging-sw.js`)
- HTTPS 배포 (FCM 필수, localhost만 예외)
- iOS: "홈 화면에 추가" 안내 UI (iOS는 설치 프롬프트 없음 → 수동 안내)

### 2단계 — FCM 연동
- Firebase 프로젝트 + VAPID 키 발급
- 클라: 권한 요청 → `getToken()` → `NotificationToken` 서버 등록/갱신
- SW: `onBackgroundMessage` → `showNotification`
- 서버: FCM Admin SDK 발송 + `notification` 큐

### 3단계 — 도메인 연결
- 상태 전이 훅 → 큐 등록 (§6 파이프라인)
- 인앱 알림센터 + 옵트아웃 설정

### iOS 제약 (요주의)
| 항목 | 제약 |
|------|------|
| 최소 버전 | iOS/iPadOS **16.4+** |
| 설치 필수 | 홈화면 추가(standalone) 안 하면 푸시 **불가** |
| 설치 프롬프트 | iOS는 자동 프롬프트 없음 → 공유 시트 수동 안내 |
| 권한 요청 | 설치 후 + 사용자 제스처(탭) 컨텍스트에서만 |
| 토큰 수명 | 설치 PWA 삭제·재설치 시 토큰 무효 → 재등록 필요 |

### Next.js (App Router) 메모
- SW는 `apps/web/public/firebase-messaging-sw.js` 정적 배치 (번들 밖, Firebase compat SDK 사용)
- 등록은 클라 컴포넌트 `useEffect`에서 `navigator.serviceWorker.register`
- `next-pwa` 도입 시 manifest·precache 자동화 가능 (단 firebase SW와 충돌 주의)
