# 요구사항 명세서


## 문제 정의
도자기 체험은 예약·결제 이후 평균 30일의 제작 리드타임 동안 사장님과 고객 사이의 정보가 단절되며, 단체 예약 시 작품-고객 매칭 비용이 과도하게 발생한다. 토담은 예약부터 작품 완성·배송까지의 한 사이클을 단일 도메인으로 관리하여 사장님의 운영 비용을 줄이고 고객의 대기 경험을 콘텐츠로 전환한다.

## 도메인
- `auth` 인증과 토큰, 사용자 세션을 관리한다.
- `partner` 파트너 capability 상태와 해지를 관리한다.
- `store` 공방 등록·검수·공개 상태와 파트너 신청 플로우를 관리한다.
- `admin` 운영자 인증 및 검수·제재 기능을 관리한다.
- `class` 공방이 제공하는 도자기 체험 상품을 관리한다.
- `reservation` 고객의 클래스 예약과 수령까지의 전체 상태를 관리한다.
- `artwork` 체험을 통해 생성된 작품의 제작 단계 상태와 사진을 관리한다.
- `review` 체험 완료 후 고객이 남기는 별점·텍스트·사진 리뷰를 관리한다.
- `notification` 상태 변경 트리거에 따른 자동 알림을 관리한다.
> `shipping` 도메인은 MVP에서 별도로 운영하지 않는다. 배송 정보는 `reservation` 및 `artwork` 도메인에서 처리한다.

---

## 접근 주체
서비스 접근 주체는 인증 여부와 capability로 구분한다. 역할(role) enum 대신 capability 기반 가드 조합을 사용한다.
- `Guest` 비인증 사용자
- `User` 인증된 사용자. 예약, 작품 조회, 수령 상태 확인 등 기본 기능을 사용할 수 있다.
- `Partner` 공방 운영 capability가 승인된 User
  - `Partner.status = APPROVED`인 경우에 해당하며, 공방·클래스·예약·작품 관리 기능을 사용할 수 있다.
- `Admin` 별도 인증 파이프라인으로 관리되는 내부 운영자. 파트너 승인, 공방 검수, 제재 등의 운영 기능을 수행한다.

### 가드 구성

```typescript
@UseGuards(AuthGuard)                  // User 이상 접근
@UseGuards(AuthGuard, PartnerGuard)    // Partner capability 필요
// Admin은 별도 모듈의 AdminGuard로 처리
```
- `AuthGuard` 유효한 access token 보유 여부 검증
- `PartnerGuard` `Partner.status === APPROVED` 검증
- `AdminGuard` Admin 전용 인증 파이프라인 검증 (별도 모듈)

# 인증 `auth`
인증은 이메일 또는 소셜 인증을 통해 사용자를 식별하고, 서비스 접근에 필요한 인증 토큰을 발급·검증한다.

## 1. 이메일 인증

### **회원가입 처리**
1. 이메일 형식 유효성 확인
1. 중복 이메일 확인
1. 비밀번호 정책 검증 (영문·숫자·특수문자 조합, 8~32자)
1. 비밀번호 해시 저장
1. 이메일 인증코드 발송 (6자리 숫자, 5분 만료)
1. 인증코드 일치 및 만료 여부 검증
1. 인증 완료 시 `User.emailVerified = true`

### **로그인 처리**
1. 이메일 형식 유효성 확인
1. 등록된 사용자 확인
1. 이메일 인증 완료 여부 확인
1. 비밀번호 해시 일치 확인
1. 인증 토큰 발급
**실패 사유**
- 유효하지 않은 이메일 형식
- 존재하지 않는 사용자
- 이메일 인증 미완료
- 비밀번호 불일치
- 비밀번호 정책 위반
- 이미 가입된 이메일
- 서버 오류

## 2. 소셜 인증

1. 카카오 사용자 식별자·이메일·닉네임 확인
1. 기존 회원 조회 또는 신규 User 생성
1. 동일 이메일의 기존 회원이 있으면 카카오 식별자 연결

1. 서비스 인증 토큰 발급
**실패 사유**

1. Google `sub`·이메일·`email_verified`·이름 확인
1. `email_verified = false`인 경우 인증 거부
1. 기존 회원 조회 또는 신규 User 생성
1. 동일 이메일의 기존 회원이 있으면 Google 식별자 연결
1. `User.emailVerified = true` 처리
1. 서비스 인증 토큰 발급
1. 사용자는 Google 로그인 버튼을 클릭한다.
**실패 사유**
- Google 인증 실패
- 미인증 이메일
- 필수 정보 조회 실패
- 서버 오류

## 3. 토큰 발급
로그인 성공 시 시스템이 인증 토큰을 발급한다.
- access token 발급 (만료 1시간), 응답 body로 반환
- refresh token 발급 (만료 14일), HttpOnly Secure Cookie로 설정
- payload에 `userId` 포함
- Partner capability 정보가 필요한 경우 `isPartner` 포함 가능

---

## 4. 토큰 재발급
access token 만료 시 사용자가 재발급을 요청할 수 있다.
1. HttpOnly Secure Cookie의 refresh token 조회
1. 만료·유효성 검증
1. 유효한 경우 새 access token 발급
1. refresh token rotation: 기존 폐기 후 새 refresh token 재발급
1. 서버에는 최신 refresh token만 유효하도록 유지
**실패 사유**
- refresh token 만료
- 유효하지 않은 refresh token
- 사용자 정보 없음

---

## 5. 로그아웃
1. 서버 저장 refresh token 무효화
1. HttpOnly Secure Cookie의 refresh token 제거
1. 클라이언트 access token 제거 처리

## 6. 회원 탈퇴
인증된 User만 수행할 수 있다.

### **탈퇴 가능 조건**
1. 승인된 Partner capability 보유 시 파트너 해지 선행 필요
1. 진행 중 예약 (`PENDING`, `CONFIRMED`) 없음
1. 제작 중 작품 (`DELIVERED`, `CANCELED`, `PICKUP_DONE` 제외 상태) 없음

### **처리**
1. 탈퇴 가능 조건 검증
1. 본인 재확인 (이메일 계정: 비밀번호 재입력 / 소셜 계정: 소셜 재인증)
1. 개인정보 익명화 (email, name, phone → 해시 식별자로 치환, OAuth 연결 정보 삭제)
1. `User.status = WITHDRAWN`, `withdrawnAt = now()`
1. refresh token 및 모든 활성 세션 무효화
1. 카카오·Google OAuth 외부 unlink API 호출
1. 마케팅·알림 수신 동의 전체 철회
1. 5년 후 자동 `DELETED` 전이 스케줄러 등록
1. 결제·예약·작품 이력은 익명화된 형태로 5년간 보관
성공
- 즉시 로그아웃
- 탈퇴 완료 페이지 이동
- 동일 이메일 재가입 30일 제한
실패 사유
- 진행 중 Partner capability 존재
- 진행 중 예약
- 진행 중 작품
- 본인 재확인 실패
- 권한 없음
- 서버 오류

# 파트너 `partner`
파트너는 공방 운영 capability를 보유한 User를 의미한다. 파트너 신청 플로우는 `store` 도메인에서 처리하며, `partner` 도메인은 capability 상태 관리와 해지만 담당한다.

## 1. 파트너 상태
- `PENDING` 첫 Store 검수 결과를 기다리는 상태
- `APPROVED` 첫 Store 검수 통과로 공방 운영 capability 활성화. Admin 개입 또는 자율 해지 외에는 변경되지 않는다.
- `REJECTED` 첫 Store 검수 반려 상태. 승인된 공방이 0개인 경우에만 적용된다.
- `SUSPENDED` 운영자에 의해 capability가 정지된 상태. 신규 공방 운영 제한, 기존 예약·작품 처리는 유지
- `TERMINATED` 파트너 자격이 해지된 상태

### 파트너 상태 전이
1. (없음) → `PENDING` 첫 Store 제출 시 자동 생성
1. `PENDING` → `APPROVED` 첫 Store 검수 승인 시 자동 전이
1. `PENDING` → `REJECTED` 첫 Store 검수 반려 시 자동 전이
1. `REJECTED` → `PENDING` Store 수정 후 재제출 시
1. `APPROVED` → `SUSPENDED` Admin 강제 정지
1. `APPROVED` → `TERMINATED` 파트너 자율 해지
> 추가 Store 반려는 Partner 상태에 영향을 주지 않는다. `APPROVED` 상태는 승인된 공방을 1개 이상 보유한 상태를 의미하며, 개별 Store의 반려 여부와 독립적으로 유지된다.

---

## 2. 파트너 자율 해지
승인된 Partner가 공방 운영을 자발적으로 종료하는 절차이다.

### **해지 가능 조건**
1. 진행 중 예약 (`PENDING`, `CONFIRMED`) 없음
1. 제작 중 작품 없음

### **처리**
1. 해지 가능 조건 검증
1. 본인 재확인
1. `Partner.status = TERMINATED`
1. 연결된 모든 Store `SUSPENDED` 전이
1. 모든 Class `INACTIVE` 전이
1. 신규 예약 차단
성공
- `TERMINATED` 전이
- 마이페이지 이동
실패 사유
- 진행 중 예약 존재
- 진행 중 작품 존재
- 본인 재확인 실패
- 권한 없음

## 3. 운영자 강제 정지
Admin이 **운영자의 정책 위반**을 사유로 파트너 전체 운영을 제한하는 절차이다. 제재 대상은 공방이 아닌 운영자이며, 연결된 모든 공방에 cascade된다.
> 개별 공방의 콘텐츠·품질 문제는 공방 노출 중단(Store 단위 액션)으로 처리한다.

### **처리**
1. Admin 권한 검증
1. 대상 `Partner.status = APPROVED` 확인
1. `PENDING` 예약 자동 취소 후 고객 통보
1. `Partner.status = SUSPENDED`
1. 연결된 모든 Store `SUSPENDED`, 모든 Class `INACTIVE` cascade 전이
1. 파트너에게 사유 이메일 통보
성공
- `SUSPENDED` 전이
- 신규 예약·공방 노출 즉시 차단
실패 사유
- 권한 없음
- 이미 해지된 파트너
- 필수 사유 미입력

# 공방 `store`
공방은 도자기 체험 클래스를 운영하는 사업장 단위이다. 1명의 파트너가 다수의 공방을 운영할 수 있으며, 각 공방은 개별 사업자등록번호를 보유한다. 파트너 최초 신청은 첫 번째 공방 등록으로 처리된다.

## 1. 공방 상태
- `DRAFT` 파트너가 정보를 작성 중인 상태
- `PENDING` 등록 완료 후 운영자 검수 대기
- `PUBLISHED` 검수 통과 후 퍼블릭 공개
- `SUSPENDED` 노출 및 신규 예약 중단

### 공방 상태 전이
1. (없음) → `DRAFT` 파트너가 공방 등록 시작
1. `DRAFT` → `PENDING` 파트너가 등록 제출
1. `PENDING` → `PUBLISHED` Admin 검수 승인
1. `PENDING` → `DRAFT` Admin 검수 반려 (반려 사유 저장)
1. `PUBLISHED` → `SUSPENDED` Admin 노출 중단
1. `SUSPENDED` → `PUBLISHED` Admin 노출 재개

---

## 2. 파트너 신청 (첫 공방 등록)
파트너 신청은 첫 번째 공방 등록으로 처리된다. User가 파트너센터에 최초 진입 시 공방 등록 플로우를 통해 파트너 신청을 완료한다.

### **등록 단계**
1. 사업자 인증 단계
  - 사업자등록증 이미지 업로드 또는 직접 입력
  - OCR을 통해 사업자명·사업자등록번호·대표자명·사업장 주소 추출
  - 사용자가 추출 결과 검토·수정 가능
  - 국세청 사업자 진위 확인 API 호출
1. 공방 정보 등록 단계
  - `공방명` 2~40자 (metadata title 사용) *필수*
  - `slug` 영문 소문자·숫자·하이픈, 4~40자, unique / 미입력 시 `nanoid` 자동 생성 *필수*
  - `주소` 도로명 주소 검색, 위도·경도 자동 변환 *필수*
  - `대표 연락처` 휴대전화 또는 유선번호 *필수*
  - `대표 이미지` 1장 이상, 최대 5MB (metadata og-image 사용) *필수*
  - `사업자등록번호` OCR 또는 직접 입력 *필수*
  - `사업자등록증 이미지` S3 저장 *필수*
  - `공방 소개` 최대 1000자 (metadata description 사용) *선택*
1. 영업 정보 등록 단계
  - 예약 오픈·마감 시간, 영업일(요일), 예약 시간 간격
  - 예약 취소 가능 조건(d-day)
  - 주차·반려동물·자동 예약 확정 가능, 여부
  - (선택) 휴식 시간 `breakStart`·`breakEnd` (단일 구간, 미입력 시 휴식 없음)

### **시스템 처리**
1. slug 중복 검증
1. 주소 좌표 변환 (외부 지도 API)
1. 사업자등록번호 형식 및 체크섬 검증
1. 동일 사업자등록번호의 `PUBLISHED` Store 존재 여부 확인
1. `Store` 엔티티 생성 (`status = DRAFT`)
1. 최초 공방 등록인 경우 `Partner` 엔티티 자동 생성 (`status = PENDING`)
1. 파트너가 제출하면 `Store.status = PENDING` 전이
성공
- 검수 대기 안내 페이지 이동
실패 사유
- OCR 추출 실패
- 사업자 진위 검증 실패
- 이미 등록된 사업자등록번호
- slug 중복
- 주소 좌표 변환 실패
- 파일 업로드 실패
- 필수 데이터 미입력

---

## 3. 추가 공방 등록
`Partner.status = APPROVED`인 User가 새 공방을 추가 등록한다. 파트너 재검증 없이 Store 등록 및 검수만 진행한다.
- 파트너 신청 플로우와 동일한 등록 단계로 진행
- Partner 엔티티는 생성·변경하지 않음
- 각 Store는 개별 사업자등록번호를 보유하며 독립적으로 검수

## 4. 공방 조회

### **진입 경로별 역할**

### **`/stores/[slug]`**** 접근 규칙**
- `PUBLISHED` 상태인 경우에만 노출. 그 외 상태는 404 처리.
- Admin은 이 URL로 접근하지 않는다. 공방 검수·노출 중단은 어드민 패널에서만 처리한다.
- 접근자 역할에 관계없이 동일한 고객 뷰를 제공한다.
- 본인 공방에 접근한 Partner는 고객과 동일한 화면을 보되, 예약 버튼은 비활성화한다.
- 공방 정보 수정·삭제·검수 상태 확인은 파트너 센터에서만 가능하다.

---

## 5. 공방 검수
Admin이 `PENDING` 상태의 공방을 검수한다. **사업자 서류 + 공방 콘텐츠를 Store 단위로 일괄 검수**한다.

### **처리**
1. 대상 Store `status = PENDING` 확인
1. 승인 시
  - `Store.status = PUBLISHED`, `publishedAt = now()`
  - 첫 공방인 경우 `Partner.status = APPROVED`, `approvedAt = now()` 동시 전이
  - 파트너에게 승인 알림 발송
1. 반려 시
  - `Store.status = DRAFT`, 반려 사유 저장
  - 첫 공방인 경우 `Partner.status = PENDING` 유지
  - 파트너에게 반려 사유 전달
실패 사유
- 권한 없음
- 유효하지 않은 검수 대상
- 이미 처리된 공방

---

## 6. 공방 노출 중단
Admin이 **개별 공방의 콘텐츠·품질 문제**를 사유로 해당 공방만 노출 중단하는 절차이다. Partner 상태에는 영향을 주지 않는다.
> 운영자의 정책 위반 제재는 운영자 강제 정지(Partner 단위 액션)로 처리한다.

### **처리**
1. `Store.status = PUBLISHED` 확인
1. `Store.status = SUSPENDED`, 중단 사유 저장
1. 진행 중 예약 유지, 신규 예약 차단
1. 파트너에게 노출 중단 사유 알림 발송
1. Partner 상태는 변경하지 않는다.
**PUBLISHED Store가 0개가 되는 경우**
- `Partner.status = APPROVED` 유지
- 파트너센터 접근 가능
- 기존 Store 수정 후 재제출 또는 새 Store 등록 가능
- PUBLISHED Store가 없으므로 신규 예약은 자연스럽게 불가
실패 사유
- 권한 없음
- 유효하지 않은 상태

# 클래스 `class`
클래스는 공방이 제공하는 도자기 체험 상품 단위로, 가격·소요시간·정원·리드타임 등의 운영 정보를 가진다.

## 1. 클래스 상태
- `DRAFT` 파트너가 정보를 작성 중인 상태
- `ACTIVE` 예약 가능, 퍼블릭 페이지에 노출
- `INACTIVE` 파트너가 일시 중단, 신규 예약 불가

### 클래스 상태 전이
1. (없음) → `DRAFT` 파트너가 클래스 등록 시작
1. `DRAFT` → `ACTIVE` 파트너가 게시 완료
1. `ACTIVE` → `INACTIVE` 파트너가 일시 중단
1. `INACTIVE` → `ACTIVE` 파트너가 재게시

---

## 2. 클래스 등록
해당 공방의 `PARTNER`만 수행할 수 있다. 공방 상태가 `PUBLISHED`인 경우에만 등록 가능하다.

### **필수 입력**
- `클래스명` 2~60자
- `가격` 양의 정수 (원 단위)
- `소요시간` 30분 단위, 30분~480분
- `정원` 1~30
- `리드타임` 10~60일 (기본값 30일)
- `대표 이미지` 1장 이상, 최대 5MB
- `수령 방법` 배송 / 픽업 / 고객 선택 중 설정

### **선택 입력**
- `상세 설명` 최대 2000자

### **처리**
1. 공방 소유 권한 검증
1. `Class` 엔티티 생성 (`status = DRAFT`)
1. 게시 버튼 클릭 시 `status = ACTIVE`
성공
- 클래스 등록
- 공방 퍼블릭 페이지에 노출
실패 사유
- 공방이 `PUBLISHED` 상태 아님
- 필수 데이터 미입력
- 권한 없음

---

## 3. 클래스 수정·중단
- 해당 공방의 `PARTNER`만 수행할 수 있다.
  - **수정 가능 필드:** 클래스명, 상세 설명, 대표 이미지, 유의사항
- 가격·정원·리드타임은 기존 예약이 1건 이상인 경우 신규 예약에만 적용되도록 분리 저장한다.
- 파트너는 `ACTIVE` 상태의 클래스를 `INACTIVE`로 변경할 수 있다.

# 예약 `reservation`
예약은 고객이 특정 클래스를 신청하는 단위이며, 신청부터 작품 수령까지의 전체 상태를 관리한다. 1건의 예약은 1건의 Artwork와 연결된다.

## 1. displayState 계산 규칙
고객에게 노출되는 상태 문구는 백엔드가 `Reservation.status`와 `Artwork.status`를 조합하여 계산한 `displayState`를 응답에 포함한다. 프론트엔드는 이 값을 그대로 렌더링한다.

```json
{
  "displayState": {
    "label": "제작 중",
    "description": "작품이 단단해지도록 정성껏 말리고 있어요.",
    "subLabel": "건조"
  }
}
```

### **계산 우선순위**
1. `Reservation.status`가 `IN_PROGRESS`가 아닌 경우 → Reservation 상태 테이블의 문구 사용
1. `Reservation.status = IN_PROGRESS`인 경우 → `Artwork.status` 기준으로 작품 상태 테이블의 문구 사용
1. `subLabel`은 `IN_PROGRESS` 구간에서만 존재하며, 나머지 구간에서는 `null`을 반환한다.

---

## 2. 예약 상태

### 예약 상태 전이
1. (없음) → `PENDING` 고객 예약 신청
1. `PENDING` → `CONFIRMED` 파트너 확인 또는 자동 확정 → **Artwork 자동 생성 + QR 발급**
1. `PENDING` → `CANCELED` 고객 또는 파트너 취소
1. `CONFIRMED` → `CANCELED` 취소 가능 시간 내 고객 또는 파트너 취소
1. `CONFIRMED` → `IN_PROGRESS` 파트너 체험 완료 처리
1. `IN_PROGRESS` + `Artwork.status = COMPLETED` + `deliveryMethod = DELIVERY` → 파트너 운송장 번호 입력 → `SHIPPED`
1. `IN_PROGRESS` + `Artwork.status = COMPLETED` + `deliveryMethod = PICKUP` → 파트너 픽업 요청 처리 → `PICKUP_READY`
1. `SHIPPED` → `DELIVERED` 발송 후 7일 자동 전이 또는 파트너 수동 처리
1. `PICKUP_READY` → `PICKUP_DONE` 파트너 수동 처리

---

## 3. 예약 생성
인증된 `User`만 수행할 수 있다.

### **생성 가능 조건**
- 대상 클래스 `ACTIVE`
- 공방 `PUBLISHED`
- 선택한 일시의 잔여 정원 1 이상
- 예약자가 해당 공방의 `PARTNER`가 아닌 경우 (자기거래 차단)

### **슬롯 유효성 검사**
슬롯 유효성은 공방의 영업 정보와 클래스의 `duration`을 함께 기준으로 판단한다.

```plain text
유효한 슬롯 조건:
  slot_start + class.duration ≤ break_start
  OR slot_start ≥ break_end
```
- 슬롯 시작 시각만 휴식 구간 밖이더라도 종료 시각이 휴식 구간을 침범하면 무효
- `breakStart`·`breakEnd` 미설정 공방은 전 구간 유효
- 유효성 검사는 클래스 단위로 수행 (같은 스토어라도 `duration`이 다른 클래스는 유효 슬롯이 달라질 수 있음)

### **필수 입력**
- `클래스` 진입 시점에 식별
- `체험 일자` 운영 시간 내, 현재 시각 이후
- `참가자명` 2~20자
- `연락처` 휴대전화 형식
- `참가 인원` 1 이상, 클래스 정원 이내
- `수령 방법` 배송 또는 픽업 (클래스 설정에 따라 고객이 선택하거나 고정)

### 처리
1. 클래스·공방 상태 검증
1. 잔여 정원 동시성 안전하게 차감
1. `Reservation` 생성 (`status = PENDING`, `source = CUSTOMER`)
1. `auto_confirm = true` 공방의 경우 즉시 `CONFIRMED` 자동 전이
1. `CONFIRMED` 전이 시 Artwork 자동 생성 및 QR 코드 발급
성공
- 예약 내역 페이지 이동
- 알림 발송
실패 사유
- 정원 초과
- 유효하지 않은 일시
- 비활성 클래스
- 필수 데이터 미입력
- 권한 없음
- 자기거래 차단

## 4. 파트너 수동 예약 등록
현장 워크인·전화 예약·단체 대리 등록 등 파트너가 손님을 대신해 입력하는 경우 사용한다.

### **등록 가능 조건**

- 선택한 일시의 잔여 정원 1 이상 (과거 일자 허용)

### **필수 입력**

### **선택 입력**

해당 공방의 `PARTNER`만 수행할 수 있다.

### **처리**
1. 예약 소유 권한 검증
1. `Reservation.status = IN_PROGRESS`
1. 연결된 `Artwork.status = VISITED` 전이
1. 고객에게 "체험이 등록되었어요" 알림 발송
실패 사유

- 유효하지 않은 예약 상태
- 체험 시작 전

## 8. 배송 처리
Artwork.status = `COMPLETED` 도달 시 deliveryMethod에 따라 분기된다.

### **배송 선택 (deliveryMethod = ****`DELIVERY`****)**
- 조건: `Artwork.status = COMPLETED` + 배송지 입력 완료
- 파트너가 운송장 번호 입력 → `Reservation.status = SHIPPED`
- 고객에게 배송 시작 알림 + 외부 택배사 조회 링크 제공
- 발송 후 7일 경과 시 스케줄러가 자동으로 `DELIVERED` 전이
- 파트너 수동 완료 처리 시 스케줄러 취소 후 즉시 `DELIVERED` 전이

### **픽업 선택 (deliveryMethod = PICKUP)**
- 조건: `Artwork.status = COMPLETED`
- 파트너가 픽업 준비 완료 처리 → `Reservation.status = PICKUP_READY`
- 고객 방문 후 파트너가 픽업 완료 처리 → `Reservation.status = PICKUP_DONE`

### **Artwork 배송 관련 필드**
- `deliveryMethod` (`DELIVERY` | `PICKUP`)
- `trackingNumber` 운송장 번호 (선택)
- `carrier` 택배사 코드 (선택)
- `shippedAt` 발송일
> 배송 실시간 추적 API는 MVP에서 사용하지 않는다. 고객은 외부 링크로 직접 조회한다.

# 작품 `artwork`
작품은 체험을 통해 생성된 도자기 1점을 단위로 하며, 예약 확정 시 자동 생성된다. 작품은 제작 구간의 세부 상태(PotteryStatus)를 관리하며, 수령 이후 상태는 `reservation`이 담당한다.

## 1. 작품 상태
작품 상태는 `Reservation.status = IN_PROGRESS` 구간에서만 고객에게 노출된다. 나머지 구간의 노출 문구는 Reservation 상태 테이블을 따른다.

### 작품 상태 전이 규칙
1. 전이는 순방향이 기본이며 정의된 순서를 따른다.
1. 파트너는 직전 단계로 1단계 되돌릴 수 있다 (오등록 정정).
1. 상태 변경 시 `ArtworkLog`에 `from`, `to`, `changedBy`, `memo`, `changedAt` 기록 (감사 로그).
1. 단계가 N일 이상 정체된 경우 `estimatedCompletedAt` 자동 보정.
1. `CANCELED`는 어떤 상태에서도 전이 가능한 종료 상태.
1. `COMPLETED` 도달 시 연결된 Reservation이 deliveryMethod에 따라 배송 흐름으로 전이된다.

---

## 2. 작품 자동 생성
`Reservation.status = CONFIRMED` 전이 시 시스템이 자동 생성한다. 예약 1건당 Artwork 1개를 생성한다. 참가 인원이 여러 명이더라도 같은 클래스를 함께 체험하므로 제작 단계는 하나로 관리한다.

### 처리
1. 예약 1건에 대해 `Artwork` 엔티티 1개 생성
1. `status = RESERVED`, `estimatedCompletedAt = 체험 일자 + 리드타임` 자동 계산
1. QR 토큰 즉시 발급 (`qr_token = HMAC(secret, artworkId + nonce)`)
1. QR 코드 이미지 생성 및 라벨 출력 가능 상태로 저장
실패 사유
- 유효하지 않은 예약

# 🚀 알림 `notification` *추후 수정
알림은 작품 상태 전이·예약 변경·배송 시작 등의 트리거에 따라 고객 또는 파트너에게 자동으로 발송된다. 채널은 카카오 알림톡 우선, 미동의 사용자는 이메일 또는 인앱 알림으로 폴백한다.

## 알림 채널
알림은 다음과 같은 채널로 발송된다.
- `KAKAO_ALIMTALK` 카카오 알림톡 수신 동의 사용자
- `EMAIL` 알림톡 미동의 사용자 또는 카카오 ID 미연결 사용자
- `IN_APP` 로그인 사용자 인앱 알림 센터

## 알림 트리거
알림은 다음과 같은 도메인 이벤트에서 발생한다.
- 예약 도메인 `예약 신청 접수` `예약 확정` `예약 취소` `체험 완료 등록`
- 작품 도메인 `작품 상태 변경` `예상 완성일 보정` `지연 발생`
- 배송 도메인 `배송 시작` `배송 완료`
- 파트너 도메인 `파트너 승인` `파트너 반려`
- 공방 도메인 `공방 검수 결과` `공방 노출 중단`

## 알림 발송
1. 알림 발송은 도메인 이벤트가 발생할 때 시스템이 자동으로 수행한다.
1. 시스템 처리
  1. 이벤트 발생 시 BullMQ 알림 큐에 작업을 등록한다.
  1. 워커가 큐에서 작업을 가져와 다음 순서로 처리한다.
    1. 수신자 식별 (사용자 또는 파트너)
    1. 채널 우선순위 결정 (`KAKAO_ALIMTALK` → `EMAIL` → `IN_APP`)
    1. 템플릿 선택 및 변수 바인딩
    1. 외부 API 호출
  1. 작품 상태 변경 알림은 내부 상태를 고객 노출 문구로 치환한다.
  1. 발송 결과를 `Notification` 엔티티에 기록한다 (`sentAt` `channel` `status` `errorReason`).
1. 응답 처리
  - `성공` 수신자에게 알림이 전달되고 발송 이력이 저장된다.
  - `실패`
    - 재시도 정책에 따라 최대 3회까지 재시도한다.
    - 최종 실패 시 `Notification.status = FAILED` 로 기록하고 어드민 대시보드에 노출한다.
    - 실패 사유를 제공한다.
      - 채널 외부 API 오류
      - 유효하지 않은 수신자 정보
      - 템플릿 변수 누락

## AI 고객용 문구 변환 (P2)
1. AI 고객용 문구 변환은 파트너가 작품 메모를 입력한 경우 진행된다.
1. 시스템 처리
  1. 파트너의 짧은 내부 메모를 변환 큐에 등록한다.
  1. OpenAI 또는 Claude API를 호출하여 고객 친화적 문구로 변환한다.
  1. 한국어 톤앤매너 프리셋을 시스템 프롬프트로 적용한다.
  1. 변환 결과를 파트너에게 검수 화면으로 노출한다.
  1. 파트너가 승인 시 알림 본문으로 사용한다.
1. 응답 처리
  - `성공` 변환 문구가 검수 가능한 형태로 제공된다.
  - `실패`
    - 변환 결과는 사용되지 않으며 파트너가 직접 작성한 메모를 사용한다.
    - 실패 사유를 제공한다.
      - 외부 API 호출 실패
      - 프롬프트 검증 실패
      - 응답 형식 불일치

## 알림 수신 설정
1. 사용자는 마이페이지에서 알림 수신 채널과 종류를 설정할 수 있다.
1. 시스템 처리
  1. 채널별 수신 동의 여부를 저장한다 (`KAKAO` `EMAIL` `IN_APP`).
  1. 알림 종류별 수신 여부를 저장한다 (`작품 상태` `배송` `마케팅`).
  1. 발송 시 사용자 설정에 따라 채널을 선택한다.
1. 응답 처리
  - `성공` 변경된 설정이 즉시 반영된다.
  - `실패`
    - 실패 사유를 제공한다.
      - 인증되지 않은 사용자
      - 유효하지 않은 설정 값
